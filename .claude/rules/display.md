# Display rules: LCD rendering, fonts, display modules

Path-scoped: Claude Code loads this file when a file matching `paths:` is read or edited, not at session start. These rules moved here from `conventions.md`, `principles.md` and `critical_lessons.md` on 2026-10-22, to keep the always-loaded corpus under the combined-size limit. Same rules, narrower trigger.

## Conventions

### Data layout

- **`constants.py` is for cross-module values only.** Per-LCD-module sizes / positions / fonts live inline in that LCD module (in tuneable-params blocks or `__init__`). Each LCD type has its own module and may pick its own sizes; sharing across modules would force false uniformity. Only add to `constants.py` if a value is genuinely consumed by ≥ 2 modules (e.g., `STOPS_WIDTH` shared by future per-train lower displays, `TIME_SCALE` shared by app + display).

### Tooling

- **`.otf` fonts only.** `.ttf` cuts (Helvetica Neue specifically) have macron/diacritic artifacts at large sizes. The `fonts/` folder should never gain a `.ttf`. Enforced by `check_fonts.py` pre-commit hook.
- **LCD fonts resolve through `font_atlas.lcd_font(face, size)`, never a bare `pygame.font.Font`, and drawn text is declared with `draws=`.** ShinGo is served from a pre-rendered atlas in a build that ships no font software, so a bare construct works in dev, where the fonts are present, and raises in that build. That is the invisible-in-dev shape of [critical_lessons §4](critical_lessons.md). Which families are baked is one tuple, `font_atlas.ATLAS_FACES`, and every font goes through `lcd_font` regardless, so no call site decides.
  - **New drawn text is a two-part edit:** the string, plus a `draws=` declaration naming where it comes from. Use `at("audio/*/route.json:stops[].name")` for data and `lit("次は")` for a source literal, with `replace=` / `split=` / `suffix=` for text the renderer derives. The atlas is cooked from those declarations, so coverage does not depend on any state being reachable, and `lcd_font` validates every draw against the declaration in dev, so an undeclared string fails on the first frame that draws it rather than in a shipped build.
  - **A `draws=` location naming a NESTED array matches nothing, and nothing says so.** Locations resolve through `fnmatch`, which reads the `[][]` in `at("audio/*/system.json:rows[][]")` as a character class rather than two literal brackets. The pattern then matches no source key, the declared string set comes back empty, and the atlas bakes without those glyphs while `check_declared` reports clean over nothing. `font_atlas._loc_pattern` escapes `[` first, leaving `*` as the only wildcard. Assert `fnmatchcase` returns True against a real key when adding a location: a silent zero-match is indistinguishable from a source that draws nothing.
  - **A `draws=` declaration wider than what the view draws weakens the check it exists for.** The declaration is the honesty gate, since `lcd_font` refuses any string outside it. Declaring `stops[].name` for a view drawing 32 of the corpus's 268 station names licenses an accidental draw of the other 236. Declare the narrowest source the view actually reads. Needing to widen it is a signal the view's data model is wrong, not a convenience. **A declaration also goes stale by standing still: changing which FACE draws a string leaves the old face's declaration covering text it no longer draws.** The E233-0 overview's small text moved to DeBold, and the Medium face kept all five locations, so the bake stored three sets of rasters nobody draws while licensing an accidental Medium draw of them. When an element changes face, move its locations with it — the declaration belongs to the face, not to the page.
  - **A font size is part of the atlas key**, so `/build` re-bakes every run. Never hand-edit a baked atlas or assume an existing one covers a nudged size. `docs/wip/WIP_font_atlas.md` holds the design, and `displays/utils.py::compose_text_parts` is the only place LCD text layout exists.
- **Never key a side table on `id(obj)`. Identity travels ON the object.** CPython reuses the address of a collected object, so an `id() -> metadata` map silently misattributes: `font_atlas` kept `id(font) -> (face, size, style)` for the fonts it handed out, and once a mode switch cleared the font cache, a bare `HelveticaNeue-Medium@24` inherited a freed `ShinGoPr6N-Medium@11` entry and got routed into the atlas. Nothing errors — the wrong metadata is well-formed. Carry the attribute on the object; when the type is a C type that rejects attributes (`pygame.font.Font`), **subclass it** (`font_atlas.LcdFont`) rather than reaching for a side table. A `WeakKeyDictionary` fixes the lifetime half but not the "unhashable / C type" half, and still separates the fact from the thing it describes. 2026-07-27; surfaced only under repeated mode switching, invisible in any single-mode run.
- **`pygame.quit()` invalidates every cached `Font` — partial-teardown when re-entering.** Tearing down the font subsystem while a module-level cache still holds `Font` objects segfaults on their next use, with no Python traceback. Any loop that rebuilds a `PASimulator` (the font-atlas bake sweeps 14 routes) must use `cleanup(full_quit=False)` — the sanctioned re-entry path (`app.py:970`) that drops only the display — then re-`set_mode`. 2026-07-27: a bake died at route 2 of 14 after 864 clean frames.
- **Iterative-preview screenshots: save + report the path, don't Read them back.** During visual tuning loops where the user is the visual judge (nudging angles/gaps/positions across rounds), write the screenshot and tell the user its path — don't Read the PNG into context each iteration; it burns tokens for no decision you're making. Read a render only when *you* must verify something (does it crash, did the element appear). 2026-05-29: user — *"for these kind of preview task, no read png to save you context."* **Save under the REPO ROOT as `screenshot_*.png`** (the `.gitignore` `screenshot_*.png` pattern keeps them untracked; repo-root paths are what the user opens) — NOT the scratchpad. 2026-07-06: user — *"all screenshot needs to be under project repo folder."*
  - **Delete your screenshots when the task is finished.** Comparison sheets, zooms and before/after pairs pile up fast, and the repo root is the author's working directory. Keep only what the author still has to look at, say which, and remove the rest. 2026-09-19, after one bug pass left 20 of them: *"next time don't spam my dirs, i know you need to compare, but clean up when task is finished"*.
  - **The don't-read-it-back exemption is per-ITERATION, not per-image — read one back when the image's PROVENANCE is new.** The first render after wiring a code path, and the first from an entry point not used this session. A render that came from stale or from the wrong source looks identical to a correct one at the command line, and handing the author its path is a claim about the live code. 2026-08-26: a 12-stop overview sheet went out rendered from a superseded layout while the new one sat unwired in a scratch script, which invalidated every earlier picture in that session. Cross-ref [principles.md § "Draw spatial structure"](principles.md), whose "read it back ONCE to confirm it rendered" carve-out covers whether it rendered, not what made it.
- **Never extract precise structural facts by reading a reference photo or screenshot.** Counts, segment cuts, alignment and member-per-row groupings are unreliable to perceive off a compressed or photographed image, and confidently mis-reading one sends a whole calibration round the wrong way. Build a faithful headless replication that reads the live tuneables and mirrors the algorithm, and read its text output as ground truth. The PNG is for the human visual judge; the algorithm is for precise facts. (2026-06-15: misread the Yamanote shinkansen wrap as 3+3 against the real 4+2, twice, off the reference PNG, while `_dev_scripts/_sim_panel_layout.py` produced the exact per-station groupings.)
  - **Measuring the REFERENCE itself needs the same discipline, and the replication route does not cover it.** When the subject is the photo rather than our render, threshold its ink inside known rects and read the bbox rather than estimating ratios by eye — an off-axis low-res photo yields a different number every time you look. (2026-08-21: the bell box's collar was read off a tilted 387px JPEG as 0.65 of the enclosure, then 0.52, in one session. A six-line bbox script settled it at once and measured our render the same way, so the two were finally comparable.)

### Display module structure

- **A new model or a new view is spec-first. Read [docs/DISPLAY.md § "Specifying a new display"](../../docs/DISPLAY.md) BEFORE writing any of it.** Three parts, in order:
  - Whole-display basics — aspect → upper/lower divide → backgrounds → canvas — are settled and drawn first.
  - Ratios are measured by script, never by eye.
  - Each view gets its own drill-down session with the author, and that session's output is the view's spec.

  The pointer lives here because the workflow fires when no renderer file exists yet, so the PreToolUse(Edit) display nudge cannot reach it. Small tuning of an already-calibrated element is exempt and goes straight to `/calibration-editor`.
- **Shared display logic uses parent + per-model concrete.** When a display module has logic shared across train models, factor a parent into `displays/<module>.py` + a per-model concrete subclass into `displays/train_models/{model}/<module>.py` — real inheritance from day one even with one concrete model. Per-model tuneables (canvas sizes, fonts) stay in the concrete (per [Data layout](#data-layout)); only shared logic moves up. **Split by rendering-vs-coordination, not by class name** — a manager's per-mode/per-slot RENDERING is per-model, but its COORDINATION (what's on screen, when it may change, what state drives it) is cross-model and belongs in the parent. Instances: `displays/transfer_info.py` (first) · `displays/lower_lcd.py` (`LowerDisplayBase` = slot cycle + force-switch + frame swap; the concretes keep renderer construction, `_pick_renderer`, `draw`). Counter-example: `UpperDisplay` stays concrete-only — its body is entirely per-model rendering. **A split is overdue when** a cross-model consumer (`ChangeScheduler`) can only reach its contract because one model happened to fork another's concrete — 2026-07-21, e235_0 satisfied the scheduler purely by subclassing e235_1000's `LowerDisplay`, so a model written standalone would have satisfied none of it.
- **Forking a sibling-model renderer: copy primitives, don't reinvent.** When intentionally duplicating a per-model renderer for a new sub-series (e.g. `e235_0/` forked from `e235_1000/` for the Yamanote re-skin), copy the existing primitive functions (pentagon draw, dot draw, chevron geometry, time-circle, etc.) verbatim into the new module — even when "I could write that in 5 lines myself" feels true. Visual-fidelity primitives encode pixel-tuned constants from prior iteration rounds (e.g. `_draw_pentagon`'s asymmetric `rect_half_w_back=21, rect_half_w_apex=20`); rolling your own loses that calibration silently and the user has to re-iterate from scratch. This is intentional per-model duplication, where copy is correct.
  - **Concept-level inheritance, not token-level transplant.** When the user names a shared concept (chevron, time circle, pentagon), find the sibling's *same-concept* primitive — full-route → full-route, not the first grep match. The sibling has multiple chevron paths (full-route asymmetric halo vs 8-station uniform-halo recipe); pick by structural role. Copy the STRUCTURAL pattern (gating logic, layered approach, shared `if gi == curr_stop:` gate, etc.); keep the concrete model's own visual params (colors, sizes) — those are model-specific. Surface "which sibling primitive is the same concept" before copying when ambiguous. The 2026-05-08 e235_0 time-circle iteration burned through 6 distinct color states partly because PASSED_COLOR (e235_1000's marker color) was transplanted instead of the structural curr_stop-gate pattern.
  - **Deployment-frame primitives don't inherit safely — re-verify against canonical homes.** Visual primitives copy verbatim, BUT deployment-frame primitives (font path resolution, asset path resolution — anything that should route through `app_paths.project_root()` per [critical_lessons.md § "PyInstaller deployment-frame divergence"](critical_lessons.md)) MUST be re-checked when forking, not blindly copied. The 2026-05-08 e235_0 fork inherited bare `pygame.font.Font("fonts/X.otf", N)` strings from e235_1000; both train models then perpetuated the same deployment-frame violation (worked in practice only because cwd happened to land at project root in dev + alongside-exe). **How to apply:** before copying a renderer, grep the source for `pygame.font.Font(`, `Path(__file__)`, bare asset strings (`"fonts/…"`, `"data/…"`), `sys._MEIPASS`, `sys.frozen` — confirm each routes through the canonical helper, then copy. (The bare-asset-string half is now also caught mechanically by `ban-derivable-literals` — see `conventions.md` § Tooling "Canonical-source duplication".)
- **Inherited slot/manager infra leaks parent bindings unless EVERY variant is overridden.** When a sub-series *reuses* the sibling's `LowerDisplay`/manager (not just copies draw functions), the parent's `__init__` constructs per-mode/per-slot renderer instances AND shared components import the parent model's dimension constants. Overriding only the common path leaks the parent's elsewhere. Two instances, both 2026-06-15: (a) **per-mode renderers** — e235_0 swapped only `japanese_display` / `japanese_eight_display` (kanji/furigana), so ENGLISH mode still showed e235_1000's linear full-route + 8-station view; fix points `english_display` / `english_eight_display` at the same instances (one shared instance, not a new one, so animation state isn't re-triggered on mode change). (b) **dimension constants** — the shared transfer display imported e235_1000's `UPPER_HEIGHT` (117), mis-sizing e235_0's lower region by 13px; fix parametrizes the dim (default = sibling's value) and reads height from the actual surface (`surf.get_height()`), never importing one model's dimension constant into shared code. **How to apply:** when forking, enumerate every renderer slot × mode the manager dispatches AND every model-dimension a shared component reads — override/parametrize all of them, not just the kanji/common path.
- **Single-slot, fixed-orientation marker → free polygon, not a parametric shape model.** When a marker is only ever drawn at ONE fixed screen position and orientation — the view re-centres on it, as with the current-stop marker that always sits at the same slot — don't build a parametric shape model with heading, side-length, tilt and pointiness knobs. Store its vertices as free-drag calibration data: the vertices ARE the shape, hand-placed against the IRL overlay. A parametric model spends its complexity on curve-following the marker doesn't have, while *failing* at the one thing that matters, matching the single photographed shape. No parameterisation can represent an arbitrary pentagon; a free vertex list trivially can. Keep the downstream pipeline — breathing scales the verts about the centroid, the halo is a uniform edge-normal offset, plus the dot — and change only the shape source. First instance: the e235_0 5-station current-stop pentagon (2026-06-12), surfaced via `/third-man` after multiple failed home-plate-plus-knobs iterations, and confirmed by the user as the firm pattern for this class of problem. The copy-primitives rule above covers the other case, a marker that moves or rotates across positions and needs the calibrated geometry.
- **Station-code badge typeface is fixed, not a parameter.** `displays/utils.draw_station_code_badge` hardcodes the face (`NeueFrutigerWorld-Bold`, the JR signage typeface) via a module-level cached `_badge_font(size)` — callers pass only point SIZES (`prefix_size` / `num_size` / `code_3_size`), never a font object. Don't re-add a font-face parameter "for flexibility": a wrong face is how the 5-station badge first rendered wrong (ShinGo/Helvetica instead of Frutiger). Size stays caller-controlled because badges legitimately differ (upper 68px → 18/22pt ≈ 0.27/0.32 ratio; 8-station 22px → 8/11pt ≈ 0.36/0.5 — chunkier so tiny text stays legible, so a single fixed ratio can't serve both). 2026-06-12: user — *"DO NOT ever change the font … that function shouldn't even accept different font."*

### UI code style

- **Tuneable-params block.** Every UI draw method must expose its magic numbers (positions, sizes, offsets, gaps) as labeled local variables at the top of the method. All downstream coordinates derive from those. No scattered magic numbers. Rationale: the user fine-tunes visuals by nudging these values — they must be discoverable AND reactive (changing `badge_w` should recompute interior width, centering, text positions automatically). **Wrap the block in `# fmt: off` / `# fmt: on`** so Black preserves trailing-comment column alignment — the alignment is what makes the block scannable. Same wrapper applies to other alignment-critical sites: aligned dict-of-tuples (`_LANG_PIXEL_FONT`-style), hex-range tables (CJK detection ranges), color-palette constant clusters. **Markers must be exact** — `# fmt: off` / `# fmt: on` only; trailing text on the directive line (e.g. `# fmt: off — preserve alignment`) is treated as a regular comment and Black formats through it.
- **Author a tuneable in the unit of whatever gate quantizes it downstream.** A change-floor deferring a dwell, a grid snapping a position, a clamp bounding a range: each transforms the parameter's effective value, so a number written in the raw unit stops describing behaviour. The lower-LCD `TRANSFER` slot was written `6.0` seconds and rendered 8s, because the 4s change floor deferred its expiry to the next allowed moment. It was correct at authoring and silently wrong forever after.
  - Express the parameter in the gate's own unit instead. Whole **beats**, via `displays/base.py` `beats(n)`, which rejects fractions, so written equals observed by construction. Validate at construction rather than trusting the author.
  - The tell is a mismatch between the source number and a measured one. Measure the effective value once per tuneable class rather than assuming the written value ships. (2026-07-21: *"we should just re-design the scheduling here, not scheduler"*. The mechanism was sound; the schedule it executed was never authored, only accumulated.)
- **Editor-compatible tuneables live in a module-level `_TUNEABLES_*` dict.** The method-local `# fmt: off` block above is its predecessor. The calibration-editor standard is a module-top `_TUNEABLES_<ELEMENT>[_MODE]` dict that the draw method reads each frame by direct key access, with no per-call recompute. To make an element editor-tunable:
  1. Extract its magic numbers into the dict, following the **param-suffix convention**. `_x` / `_y` / `_w` / `_h` / `_color` / `_<edge>_offset` drive the editor's ruler and swatch visualization. A region's position and size go in a sibling `_TUNEABLES_*_RECT` dict, which the draw method syncs via `RECT.update(...)` each frame.
  2. Keep or declare a hit-test rect.
  3. Add a `_REGISTRY` entry in `_dev_scripts/calibration_editor.py`: `rect_attr`, `dicts`, `target`.
  4. Smoke-test with `uv run preview_display.py --edit`.
  - **Convert lazily**, only when an element is next touched for tuning. There is no eager backfill sweep. New train models wire elements from day one, and `e235_0` is the golden-template fork source. Full mechanics and the suffix table are in the `/calibration-editor` skill.
- **`pygame.Font.render` clips a glyph that overflows its own surface (vertical).** `render` returns a surface exactly `get_height()` tall (`ascent + |descent|`), and at small sizes FreeType's grid-fitting inflates a glyph past that. One pixel, but a pixel of ink: over the 251 characters E233-0 draws it hits 向 城 成 片 行 越 at size 26 and 越 at 29, and `行` is on every destination. By size 38 nothing overflows. Render below the threshold at a whole multiple above it and resolve down (`_cell_scale`, `_CELL_MIN_RENDER`), so an element already large enough pays nothing. The downscale is also real antialiasing, and the glyph gets its true proportions rather than grid-fitted ones: 東's ink is 1.000 of the em at 26 and 0.950 at 80, and the reference agrees with 0.950.
  - **Grid-fitting is a WEIGHT and a PLACEMENT fault too, not only a size one.** Snapping the outline to the pixel grid rounds every stem up, so small text renders bolder than the face really is, and it seats each glyph's ink at its own sub-pixel height, so a run drawn character by character visibly walks. The author reported both on the E233-0 overview at 11px: *"reconsider font weight, seems bolder"* and *"at this small size, font type is unstable, sometimes higher sometimes lower, the placement"*. One fix answers all three, and it is the resolve-down above — but it has to cover the WHOLE run in one surface, because per-glyph downscaling puts each glyph back on its own grid. Compose at the multiple, resolve once, blit. (2026-09-02.)
  - **Choose a FACE by ink coverage, and treat a figure off a capture as a floor.** Coverage is ink mass over the ink bbox, so it separates weight from size and two runs at different sizes compare where a threshold count cannot; `_e233_lower_geometry.py --ink` reports it as `cover`. The measurement is only half an answer, because a resampled capture loses coverage at every edge — the bleed grows the bbox faster than it grows the mass — so the reference's true weight is at or above what it reads. The E233-0 destination face was picked this way and its comment says so; the overview's small text re-derived the technique without reading that, and called DeBold on a number that also admits Heavy. Validate the instrument on one string measured in both images before trusting any gap, and let the author's eye settle what remains.
- **A monospaced cell clips a glyph wider than the cell (horizontal).** Kana carry side bearing and sit inside a narrow cell, while a dense kanji fills its em edge to edge and hangs off the row surface, so 次 lost 2px at the left. Measure the overhang over the glyphs actually drawn, pad the surface, and return the pad so the caller still positions the cell origin. Any figure fitted against the pre-fix raster must be re-fitted, since the resample changes what was measured. (Both 2026-08-25, both found by the author's eye and neither by a gate: all three references read `ただいま`, so no reference frame could have shown either.)
- **To reproduce artwork from a reference, trace a COVERAGE FIELD with marching squares, never a binary mask.** A threshold is too strict and too coarse at once, and those are one fault: it discards the antialiased rim so shapes come back eroded, and it pins every vertex to an integer so curves come back as staircases. Coverage is each pixel's position along the background-to-ink axis, traced at the half-coverage line, which keeps the rim as a fraction and puts vertices wherever that fraction says. Three things follow that a mask cannot do:
  - A stroke one canvas pixel wide has no interior to a mask, so a boundary walk doubles back and fills as a hairline. Every cane, crutch and seat bar on the 優先席 placard is one.
  - An enclosed region of the background colour is invisible to an ink-only filter. Marching squares emits the placard's white heart as its own loop for free.
  - Solid-versus-hole is then a winding question, and screen-space y flips the convention. Key on the sign of the figure's largest loop, which is a solid by construction, rather than on the algorithm's handedness — handedness assumes it drew every body in the background colour and every hole in the ink, i.e. five outlines.

  What lands in the repo is a coordinate table a person could have digitised, not pixels; the licensing framing is `THIRD-PARTY.md` § "Renditions of signage designs". (2026-08-30, `_dev_scripts/_e233_lower_geometry.py --trace`.) The free-vertex rule under Display module structure above is the same idea from the other side: a fixed-orientation mark IS its vertices, and a fused silhouette, an adult holding an infant, is what no parametric body can express.
- **Any supersample-then-`smoothscale` helper must pre-fill its work surface with the ELEMENT'S OWN colour at zero alpha, never with white or transparent black.** `smoothscale` averages RGB and alpha independently — it does not premultiply. So a filled edge resolving against a differently-coloured transparent background comes back part that colour, and every antialiased edge the helper draws carries a fringe. `displays/utils.py::draw_aapolygon` filled with white at zero alpha, so every polygon in the project was rimmed pale. On an orange shape against an orange bar that rim reads as a seam INSIDE the shape; on a near-black element it reads as a glow. Filling with the draw colour makes the blend a no-op in RGB, so only alpha varies across the edge, which is what antialiasing is for. Same fault, same fix, in the upper LCD's `outlined` and the lower LCD's position marker.
  - **When the author's eye disagrees with the render and the tuneables look right, suspect the shared helper before re-tuning anything.** 2026-08-28: the seam was chased through three placement changes before the helper was read.
- **Two shapes that must touch derive their shared edge from ONE number, already snapped.** `pygame.draw.rect` rounds its edges and `draw_aapolygon` truncates its vertices. A coordinate that is an integer in the source cannot expose the divergence; one derived from measured floats does, the moment it lands a hair under a whole pixel. `605.3 − 19×30.09 − 9.59` is `23.999999999999996`, so the bar's rect drew from 24 while the triangle growing out of it stopped at 23, leaving one column of background between them. The author's eye caught it: *"the triangles is not touching with the route bar"* (2026-08-29). It arrived with a refactor that replaced integer wall literals with derived pads, so the rendering was correct until the arithmetic became real. Snap the shared value with `round()` where it is computed, not at each call site: a second `int(round(...))` at one of two consumers is the same bug wearing a fix.
- **A depth cue that works by DARKENING fails at the black end of the range — mix toward the face, not toward black.** On a near-black element, "the shaded side is darker" has nowhere to go. The shaded face and the surface it belongs to both land on black and merge into one flat mass, so the relief the cue was drawing disappears. Mix the shaded surface *toward its own face colour* instead: it still reads as the darker of the two, and stays distinguishable. Symmetrically, a highlight on a near-white element mixes toward the face rather than toward white. 2026-08-21: the departure-bell cap's side wall was `mix(lo, black, 0.35)`, which turned a proud black button into a tall black slab with no visible thickness (`departure_bell.py` `cap_wall_mix`). Relevant anywhere an element is drawn near either end of the tone range, which on this project means most things sitting on the LCD's black.

## Principles

#### A parameter the score cannot see is not being fit
Fitting a shape to a reference only fits the parameters some sample bears on. Anything else is free and drifts while the number improves. List the parameters and name the sample constraining each; one with no answer there is decoration.
- (2026-08-25) A station-plate fit scored ten cuts and none on the right edge, so `w` wandered 0.9px while the RMS fell. Adding right-edge cuts raised the score from 4.75 to 5.06, and that rise is the honest number.
- (2026-08-25) A clock-face comparison held `y` fixed across candidates, but each face seats its digits at a different height, so the fixed y was a handicap unrelated to the face. Per-candidate best y and right edge reversed the answer and took the score from 75 to 24.
- (2026-09-19) The E233-0 prefix was fitted on ただいま alone then drawn for every form, while two captures each of 次は and つぎは sat unused in the reference folder. 次は came out 17% too small and the stacked つぎは / 終点 scored worse than drawing nothing. A fit on one member says nothing about members it never scored.

**Measuring off a capture:** a number read off a photograph or screenshot carries the resampler's artefacts as well as the artifact's, systematically, so they look like features rather than noise.
- On an upscaled capture, a band brighter than both neighbours is resampling overshoot, not ink. Profile a plain edge of the same two colours elsewhere in the image and check the colour: the fabricated "white" peaked at `(252,187,151)`, pink rather than neutral. (2026-08-28: the pale bands between the E233-0 chevrons were modelled as a white outline and drawn — a whole element invented out of the capture, and the author saw it at once: *"what was that?"*)
- Measure a sub-pixel feature by its integral, not its extreme pixel. The phase moves per capture; the quantity does not, and it is also what makes a threshold-derived extent wrong. (2026-08-25: a ~1.2px line's darkest pixel read 43 on one reference and 64 on another while their integrated ink agreed to within 1%.)
- After a resample, an artifact touching its own surface edge is not evidence it was cut. A downscale's antialiasing tail legitimately reaches the edge. Test upstream (does the source render have room) and downstream (does the drawn ink land outside its clip rect).
- **A property that varies along an axis the DESIGN cannot vary along is the capture.** The E233-0 overview draws the loaded train's own service heavier, and the integral read that highlight at 4.83 on one row against 3.31 on the other; it was carried as a per-row pair for want of a second reference. The highlight belongs to the SERVICE, so a band cannot hold an opinion about it. Before encoding an asymmetry one capture shows, name what in the design could produce it — nothing can means the capture did. (Author: *"think this is a reference error"*.)
