- **"Vibe-coding mess" vs "dead feature during development"** are distinct categories. - **`__init__.py` as "model manifest"** is the cleanest pattern for shared per-model values when you have ≥2 sibling modules in a package — neither sibling is "the boss" over the other.

# 2026-04-27 — Auto-input system end-to-end (OCR → state machine → in-process integration)

Session began 2026-04-26 evening with the project-direction discussion (captured in 2026-04-26.md "Future-direction discussion" section), continued past midnight into 2026-04-27 building out the auto-input system. **Validated against live Keihin-Tōhoku 727B Omiya→Kanda drive — flawless multi-station auto-fire with single-PA + multi-PA mix.** This closes the original 3-year companion-app loop.

## Arc

**Phase 1 — Capture pipeline.** dxcam (DXGI Output Duplication) is the only reliable path for DirectX games. PrintWindow + BitBlt-from-desktop both return black frames even with `PW_RENDERFULLCONTENT` because the GPU swap chain isn't visible to GDI. dxcam reads the GPU framebuffer directly. `output_color="BGRA"` is native (no opencv dependency); `"RGB"` requires opencv-python. DPI awareness via `ctypes.windll.shcore.SetProcessDpiAwareness(2)` must be set before any window measurement. **Window detection via win32gui is unreliable** — game can have multiple windows with title-substring match; switched to grabbing full desktop (game runs at 2560×1440 fullscreen so HUD coords are fixed).

**Phase 2 — Distance OCR.** HUD bbox `(2200, 20, 350, 480)` at 2560×1440. Distance value cell at HUD-relative `(120, 314, 230, 55)`. Pipeline: grayscale → threshold (`<70`) → column-sum > 2 → bbox runs → digit-shape filter (`h≥22, 7≤w≤30`) → exact-pixel template match against 10 digit templates. Needed two non-obvious filters:
- **Text-band restriction** `y=15..52` to skip top/bottom borders + scenery bleed (frames where dark sky/buildings show through HUD's semi-transparent bg make column-detection trip on every column, merging digits into one giant blob).
- **Gap-stop at first horizontal gap > 20** to stop accepting digits past the 'm' suffix or any HUD ornament beyond the value.

Validated 6/6 reference frames + 24/24 in a live drive (mid-segment to arrival). Lower-bound match score ~0.75 in worst frames; danger zone is ~0.55 (random-match baseline 0.5 for binary).

**Phase 3 — Badge classifier.** "Next" / "次停車駅" vs "Stopping at" / "停車中" pentagon badge. Critical insight: **same green pentagon shape, only text content differs** — color sampling alone cannot distinguish. Solution: pixel-diff against 4 anchor templates (Moving-EN, Moving-JA, Stopped-EN, Stopped-JA), lowest mean-abs-diff wins. Language-agnostic for free. Diff < 15 = high confidence; transient spikes 70+ at exact transition moments are normal (badge mid-animation). Tighter `BADGE_BBOX = (15, 117, 125, 45)` after user noted leftover gray padding from the initial crop.

**Phase 4 — Speed OCR.** Same digit font as distance, reuses templates. Initial gap-based stop at decimal point (~16px gap) failed in two ways:
- **'1x.x' values** (e.g. 18.X): inter-digit gap from narrow '1' to wider next digit is ~12px, breaking with `SPEED_MAX_GAP=10`.
- **'11x.x' values** (e.g. 110.7): '1'→'1' kerning gap is ~18px, breaking with any reasonable gap threshold.

Fix: explicit decimal-point detection. Find a small bbox (`h≤10, w≤7`) in the bottom half of the text band — that's the decimal. Use its x-position as a hard stop. Robust to gap variance. `SPEED_MAX_GAP=25` becomes a safety net for cases where decimal detection misses (rare). Validated against 17 live frames spanning 0–120+ km/h.

**Otsu's adaptive threshold tried + reverted.** HUD has 3 pixel populations (text + bg + scenery bleed-through). Otsu's "best 2-way split" picks the wrong boundary when scenery contributes a third population. Fixed threshold of 70 with text-band restriction is more stable. Lesson: Otsu is great for 2-population images; multi-population needs domain-specific preprocessing.

**Phase 5 — State machine + per-segment fired flags.** `PaEventDetector` tracks distance + speed + badge. Events:
- `BADGE_STOPPED→MOVING` (segment boundary, reset flags)
- `SPEED_UP_30` (fire departure PA when speed crosses 30 km/h upward)
- `DIST_DOWN_<lead>` (fire arrival PA when distance crosses lead threshold downward; default 900m, `--lead 1200` for transfer hubs)
- `BADGE_MOVING→STOPPED` (arrived at platform)

Per-segment `departure_fired` / `arrival_fired` flags reset on `STOPPED→MOVING`. Without these, transient OCR misreads (e.g. speed momentarily reading `7` between two `>30` reads) would re-trigger threshold crossings. Initial design used `DIST_JUMP_+` (distance suddenly increases = train arrived at station, next-station distance loaded) for segment boundaries — replaced by badge transitions, which are unmissable and don't depend on distance OCR cleanliness.

**Phase 6 — PA-count check.** User's spec: skip arrival fire when next stop has only 1 PA (the only PA was already played as the departure announcement). Separate-process version loads `route.json` via `--route` flag and tracks segment count from BADGE transitions. In-process version reads `sim.stops[sim.state.curr_stop].pa` directly — simpler, no parallel route loading.

**Phase 7 — Synthetic keystrokes (1b) shipped, then pivot to in-process (1a).** First integration was separate-process: auto-driver script sends synthetic PageDown via `keyboard.send`. **Polling-miss issue surfaced:** simulator uses `keyboard.is_pressed()` polling (not event hooks), so a microsecond press-release is invisible between polls. Fix: explicit press-release with 100ms hold via `keyboard.press` + `time.sleep(0.1)` + `keyboard.release`. Working at this point — Keihin 727B Omiya→Kanda drive validated multi-station auto-fire end-to-end, including correct PA-count skipping for single-PA stops and proper firing for multi-PA stops.

User then suggested in-process integration (1a) since several issues were stacking up (synthetic keystroke timing, segment counter parallel to `state.curr_stop`, parallel route loading via `--route`). **Pivoted to 1a:** new `auto_input.py` module at project root, `AutoDriver` class spawns daemon thread, sets `PASimulator.pending_next_pa = True` instead of synthetic keystrokes. Simulator's `_handle_input_main` checks this flag alongside `keyboard.is_pressed("page down")`. Same code path, no synthetic keystrokes, no IPC, no parallel state.

Manual-press precedence becomes implicit in 1a: auto-driver inspects `sim.state.curr_stop` and `sim.state.cnt_pa` directly. If user pressed PageDown manually (advancing state), the auto-driver detects mismatch via segment_start_stop snapshot + cnt_pa check, and skips its own fire. No keyboard hooks needed in main app, no self-press guards.

## Durable insights

- **dxcam is the only path for DirectX games.** PrintWindow returns black even with `PW_RENDERFULLCONTENT`; BitBlt from desktop DC also returns black for GPU-rendered content. Same conclusion Discord/OBS arrived at.
- **Game window detection via title-substring match is fragile.** Multiple windows can match (the cracked install had a launcher window matching "JR EAST Train Simulator"). Better: identify by client-area dimensions or just grab full desktop and crop by HUD position.
- **Otsu thresholding fails on 3-population pixel distributions.** HUD has text + bg + scenery-bleed; fixed low threshold (70) with text-band restriction is more reliable than adaptive thresholding.
- **Decimal-point detection by shape beats gap-based heuristics.** Speed values 1x.x and 11x.x have inter-digit gaps that exceed any reasonable digit-gap threshold. Find the small low-y bbox; use its x as hard stop.
- **Badge state needs text-content matching, not color.** Both Moving and Stopped badges use the identical green pentagon. Only the text differs. Pixel-diff against anchor templates is language-agnostic.
- **Polling-based keyboard detection misses microsecond press-release.** When sending synthetic keystrokes to a target that polls (not event-hooks), explicit press + hold + release is required. ~100ms hold reliably overlaps multiple poll cycles.
- **In-process integration eliminates several classes of issues.** Synthetic keystroke timing, parallel route loading, parallel segment counter, self-press guards — all become unnecessary when the auto-driver shares state with the simulator. Sometimes the cleanest separation isn't the right separation.
- **Numpy-based crop in BG thread > pygame-based crop.** Pygame Surface ops are mostly thread-safe but mixing display-thread and capture-thread access invites subtle bugs. dxcam already returns numpy arrays; slicing + channel-reorder is cheap and isolating.
