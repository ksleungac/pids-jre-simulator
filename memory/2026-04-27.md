## Preferences/conventions reinforced

- **"Vibe-coding mess" vs "dead feature during development"** are distinct categories. Vibe mess = unnecessary forks/abstractions/duplications introduced by AI sessions with limited view of the whole. Dead-feature code = intentional dev byproduct (e.g. `PASimulator.small_size` — built, decided against, lingers; user considers normal). ASK before flagging borderline cases.
- **Inheritance > duplicate-and-sync** when two classes share intent to diverge later. The duplicate-and-manually-mirror approach silently bites when one class gets a bug fix and the other doesn't (e.g. the recent `band_bottom_y` clamp work would have needed manual mirror into `FuriganaDisplay`).
- **Per-model architecture direction**: per-model values (LCD dimensions, palette) live in the model package's `__init__.py`. Top-level `constants.py` is for TRULY cross-model values only.
- **Forward-looking architecture deserves a dormant marker, not deletion.** When infrastructure has a clear future trigger (multi-model, cycler split), mark it — don't remove the scaffolding just because nothing calls it today.
- **CONTRACT pointer wording**: avoid ambiguous absolutes like "UNCONDITIONALLY" without specifying the universal-quantifier scope. "BEFORE X (not inside Y)" reads cleanly even to a fresh reviewer who doesn't yet understand the architecture.
- **`__init__.py` as "model manifest"** is the cleanest pattern for shared per-model values when you have ≥2 sibling modules in a package — neither sibling is "the boss" over the other.
