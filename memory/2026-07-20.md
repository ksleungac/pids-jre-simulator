## Session (block 3): mobile-support question → LAN window mirroring (stage 1 shipped)

Started as pure discussion on contributor issue #1 (探索移动端/平板支持) and a long-standing "move to web?" thread. Landed on a built, verified feature.

**Why not a port.** Two renderers is the whole argument — every train model and every calibration round paid twice, on a project whose value IS the calibration. Backed by two facts the thread hadn't surfaced: `audio/` is 558 MB (12–140 MB per line), so no WASM/mobile bundle; and OCR is structurally PC-only, so a standalone build permanently forks the product into with/without auto-drive. The #1 contributor had already hit the same wall from the Kivy side and shelved it. Standalone-without-PC stays explicitly OPEN, not answered — streaming requires the PC.

**The design got overturned twice, both times correctly.** (1) I specced an "offscreen render target" as a prerequisite for streaming; the `/third-man` proved the coupling was invented (`.copy()` on a subsurface already returns a standalone Surface) and that my two justifications — headless, renderers-unchanged-so-free — don't survive the code (setup calls `set_mode` unconditionally; a scaled blit silently breaks `_handle_lcd_click`/`_update_hover_cursor` coord math). I'd briefed it neutrally per the 2026-07-18 lesson, and that's why it could rescue me. (2) The user then clarified *"offscreen is just by my usage"* + *"copies whatever the app is on PC"* — meaning mirror the WHOLE window, not the LCD. pygame has one global display surface, so the server just reads `get_surface()`: no frame-source registration, no `PASimulator` involvement, `app.py` untouched. The clarification made the design smaller than either of my versions.

**Two bugs, both mine, both found by the user actually using it — same shape.** Async sampling read the surface mid-draw → torn frames the user saw as flashing on e235_0 transfer pages (most elements to redraw = widest tear window). Fix: hook `flip`/`update`, capture on present. Then `image-rendering: pixelated` — right for AA-off TIMS chrome, wrong once the stream carries AA-on LCD text too, and actively destructive on the phone's DOWNscale. Fix: 1:1 device-pixel mapping, i.e. stop resampling rather than pick a filter. Both are "a simplification dropped a constraint that was still load-bearing" → codified.

**Unexpected finding.** At 1:1 the stream is SHARPER than the app's own window — Windows 125% display scaling softens the native window, and the stream bypasses it. Every calibration round to date has been judged through that resample. User: *"scaled mode is just windows's scaling of 125%"* → filed #72 as an open question (DPI awareness makes it sharp but physically smaller; the rescaling approach is undecided and the user will supply more).

**Also corrected mid-flight:** `local_ip()`'s route-to-8.8.8.8 trick returned the NordVPN tunnel (10.5.0.2), not the Wi-Fi LAN (192.168.22.190). No way to tell a VPN tunnel from a LAN by address alone — 10.x is legitimately both — so it returns a candidate LIST now. CONTRACT block at the function so it doesn't get "simplified" back.

Zero new dependencies (stdlib `http.server` + pygame's PNG writer). PNG over JPEG was measured, not assumed: on AA-off content PNG is 4x smaller AND pixel-exact where JPEG damages 6.8% of subpixels.
