### Through-service variant pattern — option (b) sibling slugs

Lines whose badge set varies by station zone (Ueno-Tōkyō: JT+JU central, JT-only south of Tokyo, JU-only north) get sibling slugs in `lines.json`. Naming convention: `<base>_<badges-joined>` (e.g. `ueno_tokyo_jt`).

Considered option (a) per-entry override — `transfers: [{"line": "ueno_tokyo", "show_codes": ["JT"]}]` — and rejected. **Why (b):** each variant self-contained at data layer (no renderer-side filter machinery, no schema growth when a future use case wants a different override field). Cost: name strings duplicate per variant. Acceptable for a small handful of through-service lines.

Captured in WIP_transfer_display.md; will distill into DATA_FORMAT.md when transfer-info promotes from WIP to production.

### Filter semantics aligned to audio

Initially proposed "keep UT visible on JT/JU trains" because I thought the audio still announced UT as a transfer. User clarified: **audio actually skips JU/JT/UT entirely on JT/JU trains.** Display matching audio is cleaner than the "more is not wrong" override. Final rule: drop any slug whose badge codes contain the active filter code (subset match `{active} ⊆ slug.codes`). Drops compound through-services like `ueno_tokyo` (JT+JU) on a JT or JU train.

### Algorithm Rule 1/2/3 refactor

Replaced the (K, H) double loop with explicit 3-rule fallthrough. **Why:** the `H` parameter (head count) was over-general — H>1 cases never fired in real data (Tokyo + Yokohama). User's actual logic is: full alignment (N≤M) or head+tail-only with even-distributed middles. Cleaning up to that shape made the algorithm readable + matched the user's mental model.

Rule 2 always even-distributes middles — no greedy anchoring there. Greedy-middle is a Rule 3 (right-edge fallback) special case for N=3 (single middle). User explicit on this distinction.
