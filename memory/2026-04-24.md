## Two bugs + a preview overhaul

Two LowerDisplay bugs fixed and the preview harness rebuilt to share code with the main app.

### Bug 1 — Global vs local index confusion in the lower LCD

Inner gold dot (current-station marker) drifted to the wrong column after the long-route final-window scroll kicked in (Keihin/Chuo at ~12+ stops in). Root cause: `draw_marks` compared `i == self.state.curr_stop` where `i` was a LOCAL index into the visible slice but `curr_stop` was a GLOBAL index into `self.stops`. While the window started at stop 0 (short routes, or long routes before scroll) the two spaces coincided and nothing broke. After scroll the slice shifted — the dot landed `stop_offset` columns ahead of the train.

**Why the fix is structural, not a patch**: threading `stop_offset` into every draw method would have left the same footgun — the next draw method someone adds can silently conflate frames again. Collapsed the accidental axis entirely:
- `_get_stops_list_disp()` returns `list[(global_idx, stop)]` tuples. Every visible cell carries its global index.
- `curr_stop_disp` redefined to live in global frame (it already was in the short-route path; only the long-route refresh had remapped it to local via the now-deleted `_refresh_curr_stop_disp`).
- All draw methods iterate `(gi, stop)` and compare state in global frame. Local index appears only in pixel-column math (`local_i = gi - window_start`) and can't escape into a comparison.

Docs updated in CLAUDE.md Key Feature #8 and notes.md "Long-Route Window Refresh".

### Bug 2 — Single-PA skip target leaks skip state forever

After fix #1 the user found that, on Keihin, departing 上野 produced correct visuals for one frame, then a SECOND PageDown left the red pointer at 秋葉原 but the gold inner dot at 神田 (one ahead). Cause: the Phase-2 skip-completion branch in `increment_current_stop_display` (`if skip > 0 and cnt_pa >= 1`) assumes the skip target has 2+ PA tracks so `cnt_pa` passes through 1 on its way up. But 秋葉原 has `pa: ["1"]` (single track) — the first PageDown at 秋葉原 already satisfies `cnt_pa >= len - 1` and jumps straight to the "advance to next stop" branch. Phase 2 never fires. `skip`/`skip_progress`/`time_to_next` leak into the next transition, permanently stranding `curr_stop_disp` one station behind `curr_stop`.

**Fix**: the `cnt_pa == 0` branch now unconditionally flushes any pending skip at its top before the regular advance. Clears `skip`/`skip_progress`/`time_to_next`, catches `curr_stop_disp` up by whatever was left of the skip. Multi-PA targets still hit Phase 2 normally (skip was already 0 by the time cnt_pa reaches 1 in the new code path, so Phase 2 is a no-op there).

**User's diagnostic framing was on the money**: "maybe wrong for when there's only 1 pa at the next station" — exactly. Worth preserving as a pattern: when state transitions hinge on a counter reaching a specific value, always check whether that value can be skipped over.

## Cursor refactor + edge-case fix (later same day)

The "deferred `curr_stop` vs `curr_stop_disp` cleanup" from above is no longer deferred — picked it up the same day after the user said "ok try try."

### What collapsed: `curr_stop_disp` is gone

The two-index split was **temporal** (PA target vs animation cursor), not spatial — they only diverge during the few seconds of skip animation. So `curr_stop_disp` was never independent state, just a denormalized cache of "where the cursor currently is" that had to be kept in sync via four separate mutation paths (Phase 1 `+=1`, time tick `+=1`, Phase 2 catch-up, single-PA flush). Each path was a place to forget something — exactly how bug #2 happened.

Replaced by a derived property on `AppState`:

```python
@property
def cursor_pos(self) -> int:
    return self.curr_stop - max(0, self.skip - self.skip_progress)
```

`skip` and `skip_progress` (already existed) fully describe the animation. cursor_pos = curr_stop when no skip is in flight; lags behind during skip; auto-catches up when skip state is zeroed.

### What fell out

- `LowerDisplay.increment_current_stop_display()` **deleted entirely** — its skip-setup logic moved to `app._next_pa`'s "advance" branch (computes `skip = curr_stop - prev_stop - 1` from the gap *after* the passing-station while-loop, not before). Its skip-catchup logic became one line in the "next PA within current stop" branch: `skip = skip_progress = time_to_next = 0`. Cursor snaps to curr_stop via the property.
- The "single-PA flush" hack from bug #2 disappears. The "advance" branch *overwrites* skip from the gap (not appends), and the "within stop" branch unconditionally zeros it. Leak class is structurally impossible — there's no dedicated "flush" path to remember.
- `_update_skip_progress` stops mutating a stored disp. Only does `skip_progress = i` at the time threshold. Cursor walks forward via the derivation.
- `jump_to_stop` dropped one line (`curr_stop_disp = target`). Already zeros skip state.

### Edge case exposed by the refactor (caught by review cycle 1)

`cursor_pos` can fall **outside the visible window** when a 2+ station skip's trailing edge sits in the long-route cut-off zone. Concretely: Keihin (46 stops, window_start=18 when refresh active), if curr_stop = 19 with skip = 2, then cursor_pos = 17 < window_start = 18. `local_disp = cursor_pos - window_start = -1`, and Python's modulo wraps to `per_line - 1`, painting the pointer at the wrong far-right column.

Pre-refactor this couldn't happen: `curr_stop_disp` was incremented one step at a time and `_refresh_curr_stop_disp` clamped it on the flip frame, so it was always within the window.

**Fix**: early-return in `draw_ptr` when `local_disp < 0 or >= len(f_stops)`. Pointer is suppressed; inner red dot at curr_stop still anchors position. Cursor reappears as `skip_progress` ticks bring `cursor_pos` back into the window.

`draw_marks` and `draw_times` are safe by construction — they iterate `for gi, stop in f_stops` so `gi >= window_start` always (no negative `local_i` possible).

### Insight worth preserving

When you have two pieces of state that are *almost always equal*, the question to ask is: "is the second one stored, or derived?" If the divergence comes from a small, named transient (here: `skip_progress` ticking through a known range), the second piece is almost always derived state — and storing it creates the bug class. Bug #2 in this file (single-PA flush) was exactly the failure mode of trying to keep a denormalized cache consistent across multiple mutation sites. The structural fix (this section) makes the bug impossible by removing the cache.
