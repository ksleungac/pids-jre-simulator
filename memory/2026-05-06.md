# 2026-05-06

## Session: v0.5.3 release shipped + PyInstaller deployment-frame pathology codified

`/build 0.5.3` produced an exe that crashed four times within an hour, all from the same family. Each crash was locally plausible; only the deployment-frame view made the contradictions visible.

The four crashes:
1. `i18n.py:app_root()` returned `Path(sys._MEIPASS)` for frozen builds. But this project doesn't use `--add-data` — `data/translations_app.json` ships alongside-exe via `/build` Step 4 copy. `_MEIPASS` was empty. Crashed on launch.
2. `data/line_icons/` not in `/build` Step 4's `Copy-Item "data\*.json"` glob (only JSONs were copied). The transfer-info renderer added this release loads PNGs from there. Crashed at first render.
3. `ocr.py:DEFAULT_TEMPLATES_DIR = Path(__file__).parent / "ocr_templates"` resolved to `_MEIPASS/ocr_templates/` in frozen mode AND `/build` Step 4 didn't copy `ocr_templates/` at all. Double-broken; crashed on `--auto-input`.
4. `auto_input.py:_get_panel_font` used `Path(__file__).parent / "fonts"` — wrong root in frozen mode even though fonts WERE alongside-exe.

A prior `/review+fix` cycle had explicitly told me to leave `i18n.app_root` alone, defending its `_MEIPASS` use as "intentional semantics." That was reasoning from generic PyInstaller mythology (SO conflates `--add-data` and alongside-exe staging). For THIS project's bundling setup, `_MEIPASS` is always wrong for project assets — only `--collect-data plotly` populates it, and only with plotly's library bundle.

The fix had two halves. Structurally: `app_paths.py` at project root with single canonical `project_root()`; 8 ad-hoc/wrong path resolvers across 6 modules collapsed to it. Bundle-coverage: `/build` Step 4 inverted from include-list (`Copy-Item "data\*.json"` + 3 explicit lines) to exclude-list (default-ship every top-level dir except `_*` / `.*` / hard-listed dev-only). Cost asymmetry argument: missing-required-asset = release crash; extra-shipped-folder = a few MB. Default-ship is safer.

The v0.5.3 release flow exposed a side issue: PowerShell backtick continuations get eaten by Git Bash, which the user runs for git ops. The multi-line `gh release create` command executed only the first line, creating an empty release. Recovery via `gh release edit` + `gh release upload` worked — flagged for `/release` skill follow-up.

The pathology-family discussion decomposed into two problems and got 3-layer codification each (authoring time / post-hoc audit / per-diff review):
- **Problem A — authoring locality** (4 helpers got duplicated because each author solved locally): `principles.md` "Search before authoring common utility code" + vibe-check smell #11 + review-dirty Lens 2 #11.
- **Problem B — under-the-radar verification** (cached PyInstaller mythology defended in review): `principles.md` "Verify deployment-frame and external-runtime semantics from primary source" (placed under Collaboration, sibling to "Verify before claiming") + vibe-check smell #12 + review-dirty Lens 1 deployment-frame check.

The cross-layer-alignment idea — when codifying a recurring pattern, fire it at all three stages — is itself a meta-rule worth keeping. Codified in session-recap as Rule 8.

`/review+fix` cycle 2 noted something worth watching: today's codification's own rules already catch existing debt the consolidation didn't reach (e.g. `tutorial.py` + `setup.py` still route through `i18n.app_root` alias rather than direct `app_paths` import). That's the rule working — the next sweep against principles + vibe-check #11/#12 will surface those without manual prompting. Tracked in TODO.

Also created `/release` skill picking up after `/build`, retired `release.ps1` (had its own bundle-coverage bug — duplicate of `/build`'s old hand-picked Step 4). The split: `/build` produces artifacts + smoke-tests; `/release` pre-flights + drafts notes + tags + hands `gh release create` to the user. Stop-before-upload, not stop-before-tag — irreversibility split.

## Session: evening — i18n cleanup + Yamanote dest-switching loader seed + validator gap-fills

Cleared two TODO follow-ups from the morning, then a substantive piece of work surfaced from a passing user question: "is the compound destination + destination switching working in yamanote?"

The TODO sweep was small. `i18n.app_root` was retired — `setup.py` (2 sites) and `tutorial.py` (3 sites + docstring) switched to direct `from app_paths import project_root`; `i18n.py` internal callers (lines 93, 159) also switched; the alias deleted. Smoke-test green. `/release` Step 7 inverted from PowerShell-backtick multi-line to a single-line `gh release create` with the version literal substituted in — works in PowerShell, Git Bash, and cmd identically. Format-rule paragraph in the skill documents WHY (Git Bash eats backticks, shell-var expansion mismatch).

Then the user asked about Yamanote. Static check on `_get_current_dest()` showed `stop_dest if stop_dest else route_dest` — looked correct. User: *"I think it wasn't switching destinations last time."* Re-trace through stops 0..29 surfaced the actual bug: between override stops, the dest reverted to route-default `品川・東京` instead of staying on the most recent override. Stop-level dest was firing only AT override stops, not sticky across inherit stops. IRL Yamanote rotates the dest through 6 sticky regions across the loop — that semantic was lost.

Discussed fix shapes. My initial framing was "walk backwards from curr_stop" — user pushed for elegance. Settled on forward-pass at route-load time: walk stops once, sticky-fill `dest` on every stop. Renderers become direct-read, no fallback logic. User then articulated the bigger principle: *"imagine the json dicts as a hint for re-creating the route data, not a one-to-one match"* — JSON is input grammar, runtime is the closure of derived fields filled in by the loader. Same shape extends to future loader-time computations (`is_first` / `is_passing` / etc.).

Implementation seeded a new `route_loader.py` at project root with `load_route_from_dir` + `finalize_route` + 3 internal computations (`_fill_dest_closure`, `_merge_station_translations`, `_resolve_dest_furigana`). `app.py PASimulator._load_route_data` collapsed to plumbing; the inline `_merge_station_data` removed (folded into loader). `upper_lcd.py:_get_current_dest` and 2 sites in `lower_lcd.py` simplified to direct read. DATA_FORMAT.md "Stop-Level Destination Override" rewritten as canonical home (sticky semantic + loader-time closure + JSON-is-input-grammar framing); DISPLAY.md collapsed its prior buggy "fallback rule" subsection to a one-line cross-reference.

Validator picked up the data-fixture conversation that started earlier. The mock catalog (`audio/_mock/main/`) had three real shape violations (first stop missing `time: 0`; three passing stations carrying `sta_cut: 0`). The user surfaced that mock translations should NOT count as drift — the catalog deliberately uses out-of-scope strings + lacks real audio. Settled on Option B: shape rules apply to fixtures (catch real preview-breaking bugs), cross-reference rules skip routes under `audio/_*/`. Validator refactored: new `is_fixture(rel)` helper, 5 new shape rules (`pa` required, `pa_at_station` forbidden on passing, `time` required on non-first non-passing, `pre_stops[]` shape, compound dest `&\n` format), `main()` split into `check_route()` + `check_compound_dest_format()`. DATA_FORMAT.md "Checks performed" rewritten into Shape / Cross-reference / Inventory groups.

Mock data fixed inline: 東京 got `time: 0`; the three passing stations had `sta_cut: 0` removed.

The discipline-lapse moment came at the verification step. After all the loader/renderer/validator changes landed, I smoke-tested only Yamanote (the bug-fix target) and said "ready to commit." User: *"How come you change something, especially it's a program already, and not re-running."* I re-ran end-to-end across all 16 routes — clean, no regression. But the trust cost was real, and the lapse was the real finding.

Recap discussion went deep on why existing customizations didn't fire. Initial framing was "Verify before claiming sibling" — user corrected: that rule fires on *defending* a claim under conversational momentum, where I re-justify from memory instead of re-reading source. This session's lapse was earlier in the chain — I didn't even claim "it works"; I just didn't think to check thoroughly. Different cognitive depth, different remedy. New entry placed in a NEW `## Engineering rigor` section, distinct from Collaboration. The two-shape-distinction matters: Collaboration verification rules cover claim-defense; Engineering rigor rules cover never-checking.

`/review+fix` cycle 1 was clean — 12 info-level findings, zero blocking. Applied one polish fix: `upper_lcd._get_current_dest` lacked the `0 <= curr_stop` lower-bound guard that the two `lower_lcd` sites had — three otherwise-mirrored sites needed consistency. 1-line tightening.
