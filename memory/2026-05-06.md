# 2026-05-06

## Session: v0.5.3 release shipped + PyInstaller deployment-frame pathology codified

`/build 0.5.3` produced an exe that crashed four times within an hour, all from the same family. Each crash was locally plausible; only the deployment-frame view made the contradictions visible.

The four crashes:
1. `i18n.py:app_root()` returned `Path(sys._MEIPASS)` for frozen builds. But this project doesn't use `--add-data` — `data/translations_app.json` ships alongside-exe via `/build` Step 4 copy. `_MEIPASS` was empty. Crashed on launch.
2. `data/line_icons/` not in `/build` Step 4's `Copy-Item "data\*.json"` glob (only JSONs were copied). The transfer-info renderer added this release loads PNGs from there. Crashed at first render.
3. `ocr.py:DEFAULT_TEMPLATES_DIR = Path(__file__).parent / "ocr_templates"` resolved to `_MEIPASS/ocr_templates/` in frozen mode AND `/build` Step 4 didn't copy `ocr_templates/` at all. Double-broken; crashed on `--auto-input`.
4. `auto_input.py:_get_panel_font` used `Path(__file__).parent / "fonts"` — wrong root in frozen mode even though fonts WERE alongside-exe.

A prior `/review+fix` cycle had explicitly told me to leave `i18n.app_root` alone, defending its `_MEIPASS` use as "intentional semantics." That was reasoning from generic PyInstaller mythology (SO conflates `--add-data` and alongside-exe staging). For THIS project's bundling setup, `_MEIPASS` is always wrong for project assets — only `--collect-data plotly` populates it, and only with plotly's library bundle.

The fix had two halves. Structurally: `app_paths.py` at project root with single canonical `project_root()`; 8 ad-hoc/wrong path resolvers across 6 modules collapsed to it. Bundle-coverage: `/build` Step 4 inverted from include-list (`Copy-Item "data\*.json"` + 3 explicit lines) to exclude-list (default-ship every top-level dir except `_*` / `.*` / hard-listed dev-only). Cost asymmetry argument: missing-required-asset = release crash; extra-shipped-folder = a few MB. Default-ship is safer.

The v0.5.3 release flow exposed a side issue: PowerShell backtick continuations get eaten by Git Bash, which the user runs for git ops. The multi-line `gh release create` command executed only the first line, creating an empty release. Recovery via `gh release edit` + `gh release upload` worked — flagged for `/release` skill follow-up.

The pathology-family discussion decomposed into two problems and got 3-layer codification each (authoring time / post-hoc audit / per-diff review):
- **Problem A — authoring locality** (4 helpers got duplicated because each author solved locally): `principles.md` "Search before authoring common utility code" + vibe-check smell #11 + review-dirty Lens 2 #11.
- **Problem B — under-the-radar verification** (cached PyInstaller mythology defended in review): `principles.md` "Verify deployment-frame and external-runtime semantics from primary source" (placed under Collaboration, sibling to "Verify before claiming") + vibe-check smell #12 + review-dirty Lens 1 deployment-frame check.

The cross-layer-alignment idea — when codifying a recurring pattern, fire it at all three stages — is itself a meta-rule worth keeping. Codified in session-recap as Rule 8.

`/review+fix` cycle 2 noted something worth watching: today's codification's own rules already catch existing debt the consolidation didn't reach (e.g. `tutorial.py` + `setup.py` still route through `i18n.app_root` alias rather than direct `app_paths` import). That's the rule working — the next sweep against principles + vibe-check #11/#12 will surface those without manual prompting. Tracked in TODO.

Also created `/release` skill picking up after `/build`, retired `release.ps1` (had its own bundle-coverage bug — duplicate of `/build`'s old hand-picked Step 4). The split: `/build` produces artifacts + smoke-tests; `/release` pre-flights + drafts notes + tags + hands `gh release create` to the user. Stop-before-upload, not stop-before-tag — irreversibility split.
