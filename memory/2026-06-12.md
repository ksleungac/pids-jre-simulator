### The badge detour — and why the Wikipedia template was a red herring
User noticed the 5-station badge "looked wrong" and thought the Wikipedia `Template:JRSN` was a more authoritative source to adopt. Chased it: expanded the template via the MediaWiki `expandtemplates` API → it's **pure CSS** (a white rounded box, colored border, line letters + number as browser-font text). No per-station artwork to download, and the browser font is *not* Frutiger. So the template is actually *lower* fidelity than what the repo already had.

The actual cause of the wrong look: the 5-station `_draw_jy_badge` was calling the shared `draw_station_code_badge` but with **bad params** — `ring_black=0` (no black frame) and the **wrong fonts** (`ShinGoPr6N` + `HelveticaNeue` instead of the upper LCD's `NeueFrutigerWorld-Bold`, the real JR signage face). Same renderer, mis-driven. Fixed by scaling the upper-LCD param set by `b/68` (upper badge is 68px).

### Font face hardcoded — `draw_station_code_badge` no longer accepts a font
User escalated to a rule: the badge function *"shouldn't even accept different font."* Refactored the helper to hardcode the face (`NeueFrutigerWorld-Bold` via a module-level cached `_badge_font(size)`) and take only point SIZES. All 4 callers migrated (e235_0 + e235_1000, upper + lower-8), dead `__init__` font objects removed.

Key constraint that shaped it: **size can't be a single fixed ratio.** Upper badge 68px→18/22pt (~0.27/0.32); 8-station 22px→8/11pt (~0.36/0.5, chunkier so tiny text stays legible). So: face fixed, size stays caller-controlled. Verified no regression on the shipped e235_1000 8-station view (sizes unchanged, face was already Frutiger).

## Session: 5-station pentagon → free polygon; editor handle redesign; digit centering

Continued the same 5-station calibration. The earlier `m0_a` parametric pentagon kept failing to match the IRL marker — I'd built home-plate + knobs (heading, side-length, right-tilt, pointiness) and an affine least-squares fit, and the user kept hand-overriding the fitted values. User invoked `/third-man` ("he draw bad, why"); the third agent's diagnosis was the unlock: I was modeling curve-following the marker doesn't have while failing to match one shape. The deciding fact (verified in code): the red marker is only ever drawn at `k==0`, a fixed slot the view re-centres on — one position, one orientation, forever. So the right model isn't a parametric pentagon (nor the third-man's suggested shear) — it's a **free polygon**: drag the 5 vertices onto the overlay, vertices ARE the shape. Rebuilt `_draw_pentagon` around a vertex list (breathing scales about centroid, uniform halo, dot); dropped `m0_a/m0_sl/m0_ra/m0_pt` + the affine-fit scripts. User confirmed free-polygon as the **firm pattern** for this class → codified to conventions.

Editor work to support it: added `v` (vertex) + initially `d` (dot) prefixes to the `five_station` waypoint config; `select_prefixes` so vertex grabs don't reselect a "station." Then two referent/visual passes from the user:
- "2 middle dots" → the dead `m0_x/m0_y` polygon anchor rendered a phantom handle. Can't delete `m0` (the `m`-handle scan starts at index 0 to reach `m1..m4`), so repurposed it as the dot anchor and dropped the separate `d0`.
- "the dot is obstructing" → **misread**: I built a `D`-key toggle to hide the *rendered* dot + a `_edit_hide_dot` production seam; user meant the editor *handle*. Reverted both. Real fix: handles → small open crosshairs, then (next ask) all handles crosshairs + smaller + two-tone (dark casing + bright core) for contrast on any backdrop.

Side fix the user spotted: 5-station countdown digits sat ~1.5px low — `get_rect(center=)` centers the surface box, not the ink. Switched to baseline + `font.metrics` ink-centering (`JapaneseFiveStationDisplay._draw_numbered_circle` only; full-route copy left as a TODO).

**State for pickup:** 5-station view NOT complete (good stopping point). Pentagon is free-polygon, vertices `v0..v4` hand-tunable in the editor; curve + station names the user is happy with. Remaining: continued fidelity tuning of the marker shape against `lcd_references/E2350.png`.
