### Piece 1 — Small-N structural rules + `rows` data override (early session)

Pre-existing context: GOLDEN-rule pipeline was at 19/22 in-spec ✓ with 3 deferred failures (秋葉原, 成田, 新橋) and a stale corpus row marking 渋谷 as failing. Spent the early session corpus-walking each failure case to find the discriminator.

Key finding: **5/5 N=3 in-spec stations IRL = `(2,1)`** and **7/7 N=2 stations IRL = `(2,)` when sum fits canvas, else `(1,1)`**. The "greedy threshold can't simultaneously gate tight-pack capacity (秋葉原 / 成田 want sub-floor inters) AND force stylistic splits (新橋 fits comfortably but IRL splits)" tradeoff that had stalled the previous session was actually a non-tradeoff — small-N IRL is structural, not threshold-driven. Pattern was hiding in plain sight in the corpus column the whole time.

Decision: small-N early-return rules in `dry_run_cascade` (N=2 → (2,) when fits; N=3 → (2,1) always) plus an optional `transfers_by_view[view].rows` data hint as last-resort fall-back for stylistic outliers. The `rows` slot is currently unused — algorithm covers all 22 in-spec stations after the rules — but exists so future stylistic outliers can be encoded as data without re-tuning.

Also discovered TWO stale corpus rows during the walkthrough (秋葉原 #14 was marked ✓ but actual algo was `(1,2)`; 新橋 #10 was marked ✓ but actual was `(3,)` — the status header was treating both as failures already; only the corpus row cells were stale).

Tight equal-spacing branch added for single-row layout when `min_inter_gap ≤ h_equal < margin_x` so 成田 (sum=612 vs canvas=618) gets sides=39, inter=39 instead of edge-pin's cramped 6 px center inter.

### Piece 2 — Step 4 column-aware anchor row placement (mid-session)

User flagged within-row anchoring issues on 渋谷 (anchoring mess), 上野 (日比谷 can't anchor under JJ), 新宿 (anchored correctly but visual weight unbalanced — Sobu's wide name should sit closer to JS than to 中央 IRL).

Long discussion proposing column-aware row 0 placement. Eventually landed on the simplest framing: **"Step 4 row 0 (or row 1 if shinkansen prefix) uses column-aware xs computed from non-shinkansen rows' max width per column; cascade Rules 1-4 unchanged below it."** Got there after the friction loop documented in Step 0 (see Codifications subsection below).

Implementation: compute `column_aware_xs` once before the per-row loop; place anchor row at those xs; rows below cascade vs the new well-chosen upper anchors via existing Rule 1 (succeeds naturally instead of falling to Rule 4 / Rule 3). Slack < 0 falls back to existing geometric `head/tail/distribute` (only 品川 + 横浜 hit this on the in-spec corpus).

User caught a regression: 1-shinkansen vs 2+ shinkansen need different treatment. With 2+ shinkansen on row 0 (Tokyo JY/JO), cascade Rule 2 already column-aligns row 1 entry 3 to the 2nd shinkansen at x=485 — overriding with column-aware on row 1 lost that alignment. Fixed with `anchor_row_idx = -1` sentinel for 2+ shinkansen case (skip column-aware override entirely).

Visible effects:
- 渋谷: row 0 JA shifts 336→297. Row 1+2 column-align via Rule 1 (was Rule 4).
- 新宿: row 0 Sobu shifts 206→224. Inter[1] = 30 (Sobu↔JS) vs inter[0] = 66 (中央↔Sobu). User's IRL "smaller gap to JS" emerges from col 0's smaller max width vs cols 1+2.
- 上野: row 1 column-aware places JJ at x=536 (was 562); 日比谷 column-aligns under JJ.
- Tokyo JY/JO: unchanged from prior cascade (row 1 entry 3 still anchors at 2nd shinkansen via Rule 2).

22/22 in-spec ✓ post-implementation. Slack<0 fall-back fires only on 品川 + 横浜 (final shapes still match IRL).
