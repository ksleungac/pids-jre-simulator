# 2026-07-18

## Session: v0.6.0 rebuild → smoke-test bug (Chūō 8-station lock + missing arrow) → cursor_pos fix + reboot-timer redesign

Rebuilt the v0.6.0 exe (post-fixes from 2026-07-16). Launched for smoke test; user found a live bug on Chūō and we fixed it + reworked the through-service reboot timing before resuming the build.

**The bug — 8-station view locked + no train arrow, departing 新宿.** Two symptoms, one root. Chūō 1654T/916H = 32 stops, dest 東京 (idx 31), 新宿 = idx 21, followed by three passing stations (代々木/千駄ヶ谷/信濃町, `pa:0`) before 四ツ谷 (25). On departure `_advance_to_next_stop` jumps `curr_stop` to the next PA stop (25) while the visual `cursor_pos` still lags at 22, animating across the skip. Both `JapaneseEightStationDisplay._get_window` and `LowerDisplay._should_lock_to_eight` keyed on `curr_stop` — so at 25 the lock fired (`32-25=7 ≤ 7` → FULL dropped) AND the window snapped to `[24..31]` with cursor 22 off the left edge (`draw_ptr` `local_disp<0` → suppressed). Fix: **both key on `cursor_pos`**. FULL now persists until the train is *visually* 7 from the end; the arrow stays in-window throughout. Verified deterministically across all routes (916 states hold the pointer-in-window invariant; sobu frames need the manager's `set_active_frame` push replicated in the harness or they false-fail).

**User's invariant (generalized):** any lower-LCD view locked to the train's position MUST always show the pointer → every stop-count/window/lock consideration is visual (`cursor_pos`). Scoped to the **active frame**; shared junctions mean the parked train is index 0 of the incoming frame, so there's no active frame without an icon. My first DISPLAY.md draft asserted a "leading-frame has no train icon" exception — I hadn't verified sobu, and it was wrong (shared junction → icon shows at 千葉). User corrected twice before I checked empirically. `principles § Verify before claiming` — I wrote a doc assertion about runtime behavior I hadn't run.

**Reboot-timer redesign.** The through-service swap hold was `sum(available slot durations)` ("exhaust all pages", ~18–30s). User: too long after arriving 千葉; *"no one cares if we exhausted all pages, I just don't want the reboot immediate after arriving."* Mental model: the hold exists to (a) signal the stop at the frame boundary and (b) let the junction's exchange (transfer) info read (the STOPPING edge force-switches to TRANSFER, so it shows immediately). Replaced with a fixed `_SWAP_HOLD_DURATION` (settled at 12s by feel; tried 3→6→12). Killed the `_swap_rotation_dur` field + the mid-page-cut TODO caveat (moot under a fixed timer).

**Review+fix caught two of my own EDIT-CONTRACT violations** (dated regression note in DISPLAY_E235, "Was … too long" change-log in DISPLAY.md — both refuse-listed history/rationale), a TODO value-drift (`3.0` vs the real 12.0), and a missing regression test. Cycle 2 caught the new test's non-ASCII PASS line crashing the cp1252 build-gate pipe (passed only because I'd set `PYTHONUTF8=1`) — the exact `conventions § reconfigure-stdout` rule. Added the guard, verified in the failing env.
