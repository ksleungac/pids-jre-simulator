## 3. CJK chrome refactor (zh-HK / zh-CN font + wrap)

Three independent issues surfaced when bilingual rendering was first attempted:

### Issue A: Helvetica-only chrome tofus CJK

Original tutorial chrome (header, subtitle, phase labels, button labels) used `_font_helv` directly. Fine for EN; CJK glyphs render as `.notdef` boxes in zh-HK / zh-CN. Switched all chrome elements to `_render_mixed(text, latin_font, cjk_font, color)` which routes per-codepoint to the right font.

Refactored `_draw_button` signature from `(rect, label, font, ...)` to `(rect, label, latin_font, cjk_font, ...)` and used `_render_mixed` internally.

### Issue B: ShinGoPr6N tofus Simplified-only glyphs

ShinGoPr6N is JIS-based (Japanese). It has Traditional Chinese glyphs (zh-HK fine — JIS overlap) but tofus Simplified-specific forms like 开, 进, 这. Need YaHei for zh-CN.

Added `_font_cjk(size, *, heavy=False)` — language-aware:
- `zh_CN` → `i18n.font_named("microsoftyahei", size, bold=heavy)` (covers Simplified)
- HK / EN → `_font_shingo(size, heavy=heavy)` (Japanese forms read right for embedded JP kanji like 国府津 / 鴨宮)

Replaced all chrome `_font_shingo` calls with `_font_cjk`. LCD station-name rendering (in `displays/`) untouched.

### Issue C: word-wrap doesn't break CJK

`paragraph.split()` returns whole CJK strings as one "word" because there are no spaces. Step 1, 4, 7 bodies overflowed the panel.

New `_wrap_atoms(text)` tokenizer yields atoms at the right granularity:
- Each CJK codepoint → its own atom (lines may break between any two CJK chars)
- Each `[[...]]` markup block → one atomic atom (don't break inside chip)
- Each Latin run between spaces / CJK / markup → one atom
- Spaces yielded separately so the wrap loop drops trailing ones at line breaks

`_draw_wrapped_text` and `_measure_wrapped_text` rewrote their inner loops to consume atoms via shared `_wrap_lines` helper.

### Issue D: keycap chip baseline misalignment

User reported `[PgDn]` / `[下一步]` chips sitting lower than surrounding CJK text. Root cause: `_render_mixed` claimed `latin_font.get_ascent()` as the chip's effective ascent for line alignment, but the chip's actual label baseline sits at `cap_y + pad_y + label_ascent` — and for CJK labels the label ascent is `cjk_font.get_ascent()`, which is larger than Latin.

Refactored:
- `_render_label_script(text, latin_font, cjk_font, color) -> (Surface, max_ascent)` — returns the inner label baseline along with the surface
- `_render_keycap(label, latin_font, cjk_font, *, kind) -> (Surface, effective_ascent)` — computes `effective_ascent = cap_y + pad_y + label_ascent` and returns it
- `_render_mixed` and `_measure_mixed` consume the tuple

Result: chip baselines align with surrounding glyphs regardless of label script.

## 4. Translations shipped

All `tutorial.*` keys now have `en` + `zh_HK` + `zh_CN` entries. Conventions:

- **Inline keycap markup**: `[[X]]` for physical keys (slate `<kbd>` chip, label NOT translated — `[[PgDn]]` stays `[[PgDn]]` in all langs); `[[btn:X]]` for on-screen buttons (green chip matching the actual button, label translated to match — `[[btn:Next]]` ↔ `tutorial.btn.next.en="Next"`, `[[btn:下一步]]` ↔ `tutorial.btn.next.zh_HK="下一步"`).
- **zh-HK voice**: concise, conversational, conventional HK Traditional spelling (出發 not 出发, 教學 not 教程, 後 not 后). Code-switching English nouns (`你已完成 Tutorial`) kept where it reads naturally.
- **zh-CN voice**: independent translation, NOT a Simplified conversion of zh-HK. Mainland register avoids English code-switching (`你已完成教程!` not `你已完成 Tutorial!`). Vocab differences applied: 教學↔教程, 廣播↔广播, 月台↔站台, 餘下↔剩余, 抵達↔到达, 影片↔视频, etc.

Translation register difference saved as auto-memory feedback (`feedback_zh_translation_register.md`).
