## 3. CJK chrome refactor (zh-HK / zh-CN font + wrap)

Three independent issues surfaced when bilingual rendering was first attempted:

### Issue A: Helvetica-only chrome tofus CJK

Original tutorial chrome (header, subtitle, phase labels, button labels) used `_font_helv` directly. Fine for EN; CJK glyphs render as `.notdef` boxes in zh-HK / zh-CN. Switched all chrome elements to `_render_mixed(text, latin_font, cjk_font, color)` which routes per-codepoint to the right font.

Refactored `_draw_button` signature from `(rect, label, font, ...)` to `(rect, label, latin_font, cjk_font, ...)` and used `_render_mixed` internally.

### Issue B: ShinGoPr6N tofus Simplified-only glyphs

ShinGoPr6N is JIS-based (Japanese). It has Traditional Chinese glyphs (zh-HK fine — JIS overlap) but tofus Simplified-specific forms like 开, 进, 这. Need YaHei for zh-CN.

Added `_font_cjk(size, *, heavy=False)` — language-aware:
- `zh_CN` → `i18n.font_named("microsoftyahei", size, bold=heavy)` (covers Simplified)
- HK / EN → `_font_shingo(size, heavy=heavy)` (Japanese forms read right for embedded JP kanji like 国府津 / 鴨宮)

Replaced all chrome `_font_shingo` calls with `_font_cjk`. LCD station-name rendering (in `displays/`) untouched.

### Issue C: word-wrap doesn't break CJK

`paragraph.split()` returns whole CJK strings as one "word" because there are no spaces. Step 1, 4, 7 bodies overflowed the panel.

New `_wrap_atoms(text)` tokenizer yields atoms at the right granularity:
- Each CJK codepoint → its own atom (lines may break between any two CJK chars)
- Each `[[...]]` markup block → one atomic atom (don't break inside chip)
- Each Latin run between spaces / CJK / markup → one atom
- Spaces yielded separately so the wrap loop drops trailing ones at line breaks

`_draw_wrapped_text` and `_measure_wrapped_text` rewrote their inner loops to consume atoms via shared `_wrap_lines` helper.

### Issue D: keycap chip baseline misalignment

User reported `[PgDn]` / `[下一步]` chips sitting lower than surrounding CJK text. Root cause: `_render_mixed` claimed `latin_font.get_ascent()` as the chip's effective ascent for line alignment, but the chip's actual label baseline sits at `cap_y + pad_y + label_ascent` — and for CJK labels the label ascent is `cjk_font.get_ascent()`, which is larger than Latin.

Refactored:
- `_render_label_script(text, latin_font, cjk_font, color) -> (Surface, max_ascent)` — returns the inner label baseline along with the surface
- `_render_keycap(label, latin_font, cjk_font, *, kind) -> (Surface, effective_ascent)` — computes `effective_ascent = cap_y + pad_y + label_ascent` and returns it
- `_render_mixed` and `_measure_mixed` consume the tuple

Result: chip baselines align with surrounding glyphs regardless of label script.

# 2026-04-30 (Afternoon) — Dep classification pathology + `data_tools` rename + deployment-frame codification

## Context

Picked up from the morning's freshly-merged `feat/i18n-language` (chrome i18n + bilingual OOBE). Discussion started about whether to cut a small v0.5.3 release without OCR. Audit revealed `dxcam` was in the `dev` dependency group while `auto_input.py` (production) imports it — meaning a release exe wouldn't bundle dxcam, and the OCR Auto-PA toggle would crash on activation. Same pattern for `plotly` (used by `plot_drive.py` via the Report-↓ button, with the production-side import wrapped in `try/except` that swallowed the would-be ImportError).

This audit kicked off a deeper diagnosis: how did the previous claude end up with this misclassification, and what would prevent it next time?

## Release-strategy decision

**Hold for v0.6.0 with OCR; don't ship a v0.5.3 small release.**

Reasoning: the audience is reached primarily via existing YouTube videos (~1800 plays). Pattern from v0.5.0→v0.5.2 was "comment update on existing video" rather than a new video — significant updates landed but didn't independently warrant a new production. OOBE bilingual + chrome i18n + STOPPING + click-jump + pre_stops are similarly real polish but not video-worthy on their own. OCR is the genuinely headline-shaped beat ("the simulator now auto-drives in sync with the game") that warrants a new video. Saving the next release for OCR's public debut concentrates the punch.

Pre-requisites for OCR public release (deferred for now): hide-toggle flag work (or full release-readiness for the toggle), warning modal (TODO line 20), multi-resolution validation, autodriver re-anchor on click-jump.

## The diagnostic deep dive — three pushes for "why"

I gave three shallow framings of the misclassification before landing on the actual root cause. User pushed back at each step:

**Push 1:** I said "two things got conflated" (lazy import + dev classification). User: *"It's the deferred import, but that doesn't mean production doesn't need that library... it's so weird..."* — sharpening: the deferral is a perf trick, but doesn't justify dev classification. Lazy controls *when* a lib loads; "optional" controls *whether* it must be installed; they aren't interchangeable.

**Push 2:** I expanded to "three contributing factors" (folder taxonomy / inherited invariants / try-except masking). User: *"But I still don't understand how come the last claude's made these mistakes, is amateur and not normal TBH., any more hint?"* — pushing for the underlying cognitive failure that explains all three, not just a list of symptoms.

**Push 3:** I articulated the root cause: claude reasons about code as **text** (file paths, dep field names, neighbor strings), not as a **deployed system** (production reachability, release-build behavior, user-facing failure modes). The three "contributing factors" are all the same pathology in different costumes — folder taxonomy = text-level (the file's path is a string, the dep classification is another string, harmonize the strings); inherited invariants without re-audit = text-level (the rule lives in a doc, doesn't fail on violation); try/except masking = text-level (the line could fail, wrap defensively without simulating what the swallowed exception means in production). User then redirected: *"I need to answer 'why' but not 'ok now this is fixed'."* — explicit signal that depth of causal analysis matters before moving to remediation.

The secondary observation: claude is fluent at **locally coherent narrative**. The chain "lazy → defer → optional → dev → data_tools" reads smoothly because each step has a plausible English justification. The smoothness is the trap. A human spotting the chain might pause at step 2 ("does deferred mean optional? no.") because they're checking against deployed reality. Claude generates the next plausible link and feels satisfied.

This diagnosis was the meat of the session. The mechanical fix flowed naturally from it.
