## Session: Yamanote compound-dest middle dot → halfwidth per IRL

While live-tuning the new calibration editor against Yamanote dest in upper LCD, user noticed the compound-destination middle dot rendered at fullwidth (`・` U+30FB) while IRL JR East PIDS uses halfwidth (`･` U+FF65). Discovery surfaced from sit-down tuning sessions — exactly the kind of fidelity gap the calibration workflow is designed to surface.

Two paths considered: (A) data swap — replace `・` with `･` in all compound-dest values + translations.json keys; (B) render-time substitute — keep data fullwidth, swap in `draw_destination` before render. Picked A. Reasoning: data files are the canonical record of "what does IRL PIDS show." Render-side substitution hides the IRL fact behind a render trick — future readers of `route.json` would see `品川・東京` and think IRL renders fullwidth. Option A makes the convention legible at the data layer.

Scope mapped via grep across `data/`, `audio/`, etc.: 14 swap sites across 3 files — `audio/yamanote/route.json` (7 occurrences: route-level dest + 6 stop-level overrides covering the dest-cycle), `audio/_mock/main/route.json` (1 occurrence: 品川･高輪ゲートウェイ — no translations.json entry exists, dest renders kanji-only there), `data/translations.json` (6 compound-dest keys: 品川･東京, 東京･上野, 上野･池袋, 池袋･新宿, 新宿･渋谷, 渋谷･品川). EN forms in translations.json unchanged because they use `&` separator, never `・`. Line names elsewhere (`lines.json` shinkansen + Liner, route headers in saikyo/sobu/keihin/joban route.json) untouched — different display elements, IRL convention may differ.

Executed with `Edit replace_all=true` per file after Read-first verification. Validator (`validate_data.py`) clean post-swap — the 53 issues it reports all pre-existing JJ Joban WIP gaps (per audio/README JY entry note from 2026-05-12); zero new issues from the dot swap. Lookup chain end-to-end verified: route dest `品川･東京` → `tr['品川･東京']` → `{'english': 'Shinagawa&\nTōkyō'}` resolves; both kanji + english screenshot renders confirm visually.
