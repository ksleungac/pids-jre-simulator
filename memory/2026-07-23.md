# 2026-07-23

## Session: dxcam capture crash on multi-GPU / hybrid machines (#97)

User report (screenshot): a Win10 / 1080p / 144Hz machine crashed the `AutoDriver` thread at
`dxcam.create()` with `_ctypes.COMError -2005270524` = `0x887A0004` = `DXGI_ERROR_UNSUPPORTED`,
raised from `IDXGIOutput1::DuplicateOutput`. PA window itself ran fine — only OCR auto-input died.

**Root cause, and the model I had to sharpen.** First framing was "hybrid GPU." The user pushed
back — *"on my pc i also have igpu, but i didn't force it, no error?"* — which was the right
correction. Ran dxcam on the dev box: 3 raw DXGI adapters exist, but dxcam only exposes adapters
with a display attached (`if len(p_outputs) != 0`), so the iGPU (no monitor on it) is invisible;
device 0 = the dGPU = the display's owner → DDA against its own output works. So the trigger is
NOT "has an iGPU" — it is *device 0 is not the DDA-capable owner of the display it's told to
duplicate*. The textbook hit is a Microsoft-Hybrid (Optimus) laptop whose captured display is
owned by the dGPU: DDA against the discrete GPU on a hybrid system is unsupported by design.
Web search confirmed this is documented MS behavior, not a dxcam bug (learn.microsoft.com;
ra1nty/DXcam #18/#38).

**Fix (no new dep).** `_open_capture_camera` + `_enumerate_capture_targets` in `driver.py`:
parse `dxcam.output_info()` into every `(device_idx, output_idx)`, primary-first, and return the
first whose `create()` succeeds (a successful create IS a live duplicator). Wrapped so a `COMError`
degrades gracefully instead of killing the thread — but the full traceback is printed on total
failure, per the user's hard requirement (*"if you mute the trace we cannot debug next time"*).
Verified: single-GPU happy path unchanged; simulated multi-GPU falls through device 0→1; all-fail
prints the trace and returns None.

**What enumeration does NOT cover.** If the *only* adapter owning the display is the dGPU on a
hybrid system, every dxgi combo raises UNSUPPORTED and enumeration exhausts — that is the winrt
(`Windows.Graphics.Capture`) residual, which needs the `winrt` package bundled (user OK'd a
bundle but preferred a no-winrt solution first). Deferred until a report shows enumeration is
insufficient. So I was careful NOT to over-claim the fix definitely helps THIS reporter — their
144Hz-laptop profile could be the winrt-only case.

**User-side workarounds handed over (opposite-direction, one matches their topology):** force our
exe → iGPU (Windows Graphics settings; works if display is iGPU-owned); or BIOS discrete-only /
disable-Optimus (removes the hybrid condition so the dGPU legally owns the display; NOT via Device
Manager — can black-screen a MUX-less panel). Each also diagnoses which sub-case they're in.
