## Session: 1080p OCR hardening — decimal-slip fix, resolution logging, decimal capture, badge-reject gate (+ report/band polish)

Long single-thread session: a railfan user reported wrong speeds at 1080p on Yamanote.

**The decimal-slip.** Speed shows as `NN.N`; the reader cut the tenths by detecting the decimal DOT, but on a softened 1080p capture the dot binarizes to ONE dark column and `finalize()` can't bbox a 1-column run → dot missed → tenths slips into the integer (`19.1→"191"`). Invisible on dev (crisp captures render the dot 2–3 columns; a live drive read 0/69). **I nearly abandoned the fix** — conceded "readers are stable" on can't-reproduce-locally + a crisp sample — until running the production OCR over the user's screen-recording reproduced it at 40%. That reversal is the session's hardest lesson → `critical_lessons.md §7`. Fix = 1-column-tolerant decimal scan (scan raw col-runs, not finalized bboxes); 1440p bit-identical, reporter video 579→0 slips. The user then reframed the whole effort: **1080p is the canonical stable target** (the future multi-res path downscales everything to 1080p), so dev-crisp 1440p is NOT the bar.

**Why we couldn't tell what res the OCR ran under.** The drive-log meta recorded nothing about resolution — so a "problematic OCR" report was unattributable and I filled the gap with theory (wrong-resolution, fragile-dot) for several rounds. Added `desktop_resolution`/`ocr_profile_resolution`/`ocr_scale` to the meta. Live proof it matters: the user's "1440p" test videos were actually 1080p.

**Decimal capture (decimals everywhere except the band).** Chose decimal-cut + a SEPARATE tenths read (`read_speed_tenths`) over read-all-÷10 — the latter has an `X.0` tenths-drop that reads 10× low; the separate read degrades a dropped tenths to `.0`, never a wrong integer. `speed` (int) drives band + decisions; `speed_decimal` logged + shown in report/console; band stays integer.

**Badge-reject score gate.** User's mechanism: when `badge is None` (classifier reject = degraded frame), gate other reads under a confidence threshold. Sampling confirmed the premise — badge=None reads sit at score ~0.60 vs ~0.90 when the badge reads. This is the CONDITIONAL floor that supplies the honest threshold the earlier global-floor ban lacked; T=0.80 (my call). Review+fix caught that my first regression fixture (`19.1→19`) didn't discriminate — `_rectify_speed(191)=19` so it passed both ways — swapped for a rectify-proof `5.3→5` → `principles § "Test real logic"`.

**Also:** confidence score is fix-invariant (distributions near-identical with/without the decimal fix). Visual polish — band unit equal-width 半角 + size 15 + tight divider gap; report speed/limit lines doubled; limit line drawn so its BOTTOM edge sits on the value (ceiling cap); report shows decimals — all pending the user's visual judgment. Nothing committed.

**Next:** user flagged the remaining-DISTANCE reading is also unstable in the reporter's jsonl — to investigate.

## Session (block 2): OCR hardening cluster + status-band unit + report polish + distance guard

**Badge-reject score gate** (`_apply_badge_reject_gate`, T=0.80). When `badge is None` (classifier reject = degraded frame) drop speed/distance/limit reads < 0.80 — sampled badge=None reads score ~0.60 vs ~0.90 when the badge reads. The CONDITIONAL floor supplies the honest threshold the earlier global-floor ban lacked.

**Distance plausibility guard** (`guard_distance`, #79 under #70). Distance spikes on degraded frames (`1372→3→1257`), 60% co-incident with speed slips; badge-gate misses them (badge reads MOVING). Physical gate: reject a change > `MAX_DRIVABLE_SPEED_KMH·Δt` (+50m), hold-last-good; ceiling speed + real elapsed Δt. **`/third-man` redirected my two-frame-consensus idea → badge-transition anchor reset** (reuses an existing signal, self-heals on double-garbage). Key refinement from the user's own question ("passing→passing / passing→moving?"): reset on ANY STOPPED/PASSING frame (prior OR current badge), so `MOVING→PASSING` doesn't false-reject — prior-badge-only would have. `badge=None` while prior MOVING stays gated (no anchor poison). Validated on the reporter logs: wild jumps 24/10 → 1/1.

**Status-band unit** — long visual iteration. User wanted the unit on the digits' monospace/fat model, glyphs touching. Landed on full-width fat forms (`ｋｍｈ`) advanced proportionally at ≤1px (touching), `/` kept natural (full-width `／` too wide). A uniform cell floated the narrow glyphs — that was the "broken" state. Also: report speed/limit lines doubled; limit line drawn so its BOTTOM edge sits on the value (ceiling cap); report shows decimals.

**PC-variability discussion (ongoing, NOT codified).** User asked why native-1080p would misread at all. Answer: OCR grabs the DESKTOP framebuffer, and DPI scaling (125% — proven to soften on the user's own machine, #72) / GPU scaling / non-native res / borderless compositing all interpolate it before dxcam sees it. Honest caveat surfaced: the reporter's VIDEO is H.264-compressed so the 40% overstates the live path — but the live JSONL also slipped, so live degradation is real. User is skeptical ("don't believe such difference, especially native res") and will have the reporter test a fresh 0.6.1 build (exe-only) — the new resolution-in-meta logging will attribute it. Drafted a suggested-settings list (scale 100%, native res, GPU no-scaling, exclusive fullscreen, no capture/RDP layer) but held it as provisional pending the reporter's test.

## Session (repo-mapping tools eval): repomix → code-review-graph, wired into review+fix

Separate concurrent session (the OCR blocks above are a parallel PC; the #78 change-scheduler is a third agent — excluded from my commit). Opened as "find easy backlog fixes" (triaged 35 housekeeping/review-finding issues via 4 parallel subagents → shortlist, PARKED), pivoted to a user-driven tooling evaluation.
