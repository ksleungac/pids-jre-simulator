## Session: 1080p OCR hardening — decimal-slip fix, resolution logging, decimal capture, badge-reject gate (+ report/band polish)

Long single-thread session: a railfan user reported wrong speeds at 1080p on Yamanote.

**The decimal-slip.** Speed shows as `NN.N`; the reader cut the tenths by detecting the decimal DOT, but on a softened 1080p capture the dot binarizes to ONE dark column and `finalize()` can't bbox a 1-column run → dot missed → tenths slips into the integer (`19.1→"191"`). Invisible on dev (crisp captures render the dot 2–3 columns; a live drive read 0/69). **I nearly abandoned the fix** — conceded "readers are stable" on can't-reproduce-locally + a crisp sample — until running the production OCR over the user's screen-recording reproduced it at 40%. That reversal is the session's hardest lesson → `critical_lessons.md §7`. Fix = 1-column-tolerant decimal scan (scan raw col-runs, not finalized bboxes); 1440p bit-identical, reporter video 579→0 slips. The user then reframed the whole effort: **1080p is the canonical stable target** (the future multi-res path downscales everything to 1080p), so dev-crisp 1440p is NOT the bar.

**Why we couldn't tell what res the OCR ran under.** The drive-log meta recorded nothing about resolution — so a "problematic OCR" report was unattributable and I filled the gap with theory (wrong-resolution, fragile-dot) for several rounds. Added `desktop_resolution`/`ocr_profile_resolution`/`ocr_scale` to the meta. Live proof it matters: the user's "1440p" test videos were actually 1080p.

**Decimal capture (decimals everywhere except the band).** Chose decimal-cut + a SEPARATE tenths read (`read_speed_tenths`) over read-all-÷10 — the latter has an `X.0` tenths-drop that reads 10× low; the separate read degrades a dropped tenths to `.0`, never a wrong integer. `speed` (int) drives band + decisions; `speed_decimal` logged + shown in report/console; band stays integer.

**Badge-reject score gate.** User's mechanism: when `badge is None` (classifier reject = degraded frame), gate other reads under a confidence threshold. Sampling confirmed the premise — badge=None reads sit at score ~0.60 vs ~0.90 when the badge reads. This is the CONDITIONAL floor that supplies the honest threshold the earlier global-floor ban lacked; T=0.80 (my call). Review+fix caught that my first regression fixture (`19.1→19`) didn't discriminate — `_rectify_speed(191)=19` so it passed both ways — swapped for a rectify-proof `5.3→5` → `principles § "Test real logic"`.

**Also:** confidence score is fix-invariant (distributions near-identical with/without the decimal fix). Visual polish — band unit equal-width 半角 + size 15 + tight divider gap; report speed/limit lines doubled; limit line drawn so its BOTTOM edge sits on the value (ceiling cap); report shows decimals — all pending the user's visual judgment. Nothing committed.

**Next:** user flagged the remaining-DISTANCE reading is also unstable in the reporter's jsonl — to investigate.

## Session (block 3): #78 lower-LCD flash fix — change scheduler → beat-authored schedule

Implemented the locked `WIP_slot_timing.md` design, then the *design itself* got reworked mid-flight by the user twice. The mechanism survived both; the schedule it executes did not.

**Structural prerequisite nobody had specced.** The slot cycler lived in the E235-1000 concrete, and e235_0 satisfied the scheduler's contract only by *happening* to fork that class — a model written standalone would have satisfied none of it. Promoted to `displays/lower_lcd.py` (`LowerDisplayBase`). The split axis is **coordination vs rendering**, not class name: what's on screen and when it may change is cross-model; how it's drawn is per-model. `draw()` is now contractually pure — that purity IS the fix for the original two-clock bug.

**The `/third-man`'s starvation trap was real but obsolete.** The locked spec split cadence 4s / floor 2s specifically to dodge it (floor == cadence + axes ticked IN TURN → a cadence-aligned slot blocks forever). Atomic evaluation already removes that trap, so the split was solving a problem the implementation had dissolved. Measured floor 4s: 10 slot rotations/120s, no starvation. **A constraint inherited from a superseded design is not evidence** — re-derive it against what actually shipped.

**Where the schedule was actually wrong (the user's reframe).** I kept fixing the *scheduler* while the user was pointing at the *scheduling*. The tell was a footnote I'd written off as a quirk: `TRANSFER` written `6.0`s **rendered 8s**, because the floor deferred its off-grid expiry. Written ≠ observed means the source stopped describing the screen, and no amount of mechanism work fixes that. Resolution: author every duration in whole **beats** (1 beat = the language cadence), validated by `beats(n)`. → `conventions.md`.

**Two corrections I got wrong first.** (1) I asserted the transfer page is language-agnostic from a code comment — true of the lower renderer, false of the screen, because the upper keeps cycling above it. (2) I built a coverage invariant on "a language-distinct slot must dwell ≥ the language cycle"; the user's actual rule is weaker and correct — coverage may span *successive* appearances. The bad invariant would have forced a needless retune. Both replaced by a *simulated* pairing-coverage check rather than arithmetic I could get wrong again.

**Review+fix caught my test rotting.** The logo-suppression assertion was mutation-proven when written, then went inert after I retuned the floor 2s→4s and changed `reveal_slot` to always return a slot — and I never re-ran the mutation. My first repair was also inert (sampled the guard pair *after* the stepped frame, so it already held the mutated value). → `principles.md`. Final state: 8 mutations, all fail the suite.

**Two defects found by tracing the real junction timeline** rather than reasoning: the logo reveal didn't restart the slot dwell when the revealed slot was already current (wall-clock timers burn dwell under a 5s logo → new segment's opening view lasted one floor, not its full dwell), and the swap fire wasn't floor-gated (a rotation could land a frame before the logo covered it — and unlike a driver stop, that fire time is *predictable*, so it can be look-ahead suppressed).

**`code-review-graph` verdict** (the block-2 session wired it; this session was its first real exercise): it fires, and `detect-changes` earns its slot. Two measured gaps — it is blind to **untracked** files (`LowerDisplayBase` + its new test returned zero hits across both scans, so the blast radius missed the largest piece of the change and the test-gap count was inflated), and it **never detects its own staleness** (`status` reports existence, not currency; nothing rebuilds it). `impact` returned 1.2 MB, not the documented ~3-4k tokens.
