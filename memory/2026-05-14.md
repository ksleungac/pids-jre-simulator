Mid-session writeback corruption incident: user pressed Ctrl+S after real value tuning, source file at `displays/train_models/e235_0/lower_lcd.py` line 75 corrupted into unparsable Python (`"arc_p3_x": 9,   "arc_p3_y":  9992  "arc_p3_stroke": 7055`). Editor crashed on next Ctrl+S because `ast.parse(text)` failed. Root cause: `_swap_dict_literal` iterated AST values forward through `zip(target_node.keys, target_node.values)`. Each replacement shifted the modified line's length, but subsequent iterations used original-AST col-offsets — second-key replacement on the same line sliced the wrong substring. The function's own comment said "Walk keys in reverse so col-offset edits on later keys don't shift earlier ones" but the code DID NOT reverse — a parenthetical justified forward iteration as safe because "each key→value is on its own line in our dicts." Phase 1b broke that schema invariant by putting 3 keys (`arc_pN_x`, `arc_pN_y`, `arc_pN_stroke`) on one line. First Ctrl+S after schema change "worked" by happy coincidence (user had only focused but not nudged any values → new_repr == old_repr → no length shift). Second Ctrl+S after real tuning detonated.

Fix landed: iteration changed to `reversed(list(zip(target_node.keys, target_node.values)))` — rightmost edits land first, earlier-col edits then use cols that are still accurate because no edit has happened to their left. User said "eye balls it" on recovery values for the corrupted line — restored to `(arc_p3_x=9, arc_p3_y=92, arc_p3_stroke=55)` based on the corruption pattern + eyeballed continuation of the decreasing stroke trend (p0=160, p1=120, p2=85, p3=55).
