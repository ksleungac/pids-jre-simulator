## Session: Re-entry (Layer 3 → Layer 2) + WIP_autodriver graduation

Closed the last open piece of the auto-driver layered-state arc: **re-entry** — pulling the
driver's belief up to the game when Layer 1 lags (cold boot mid-drive, mid-transit click-jump,
missed OCR). The user framed it as "Layer 3 → Layer 2" and drove the design rule-by-rule,
keyed on Layer 3 state:

- 3A/3E parked → no-op. 3B (speed<30) → no-op; the normal `SPEED_UP_30` crossing fires it
  with audio. 3C (cruising) → silent advance to 1A. 3D (arriving) → silent advance to 1B.
- The user's key worry was propagation — "if 3D advances Layer 2+1, how about the coupling
  reading back to Layer 2?" Resolved: the shipped Layer 1↔2 coupling is **read-only on Layer 1**
  (it reads for the segment label + fire-gate, never writes the observed-flags), so re-entry
  writing Layer 1 + flags as one consistent snapshot doesn't cascade. One-way DAG, not a cycle.

Why two halves matter: re-entry = "game → Layer 1" (silent advance) AND "Layer 3 → Layer 2"
(seed the observed-flags). Same act, written together; the consistency of the pair is what
makes it loop-free.

**Plan finalized via /third-man (sonnet)** before coding (multi-file structural change). Its
load-bearing catch: my first plan had the bg OCR thread mutating `AppState` directly — torn
multi-field reads against the render loop. Fix = single-shot `pending_silent_advance` signal
(bg writes, main thread consumes via `_silent_advance_to` → `_advance_to_next_stop(silent=True)`),
exactly the `pending_next_pa` precedent.

**Refinement I added over third-man's draft:** re-entry stands down whenever `pending_next_pa`
is already set. That's the discriminator between a *live* 3B→3C departure (fires with audio via
the normal crossing) and a *re-entry* 3C (silent). It does NOT suppress arriving-while-parked,
because there `_fire_arrival` skips (app parked) so `pending_next_pa` stays False — the case
still gets its silent 1B advance. Validated by 11 isolated detector traces (no live game),
then the user live-drove it OK.

Re-entry **subsumes** the two previously-deferred entry-point cases (mid-transit click-jump +
toggle-ON cold entry) for free — the `_reanchor_to_app` OCR-memory reset still runs on click,
then `_maybe_reentry` does the advance.

**Graduation:** with the coupling + re-entry both live-validated, dissolved `WIP_autodriver.md`
into `auto_input/README.md` (new § "Re-entry") and deleted it (per the WIP-graduation convention).
Validation history → git + dailies; calibration insights already mirrored in README/code
(DPI-awareness lives in code + memory/2026-04-27). In-code WIP refs repointed to the README.

Plot detour (non-bug): user thought the drive-report HTML wasn't opening — it was saving fine
(5 MB), just never auto-opened (no `webbrowser.open` in the report flow, never was). Then asked
why the plot looked clean despite testing re-entry — answer: re-entry writes no JSONL event
(intended), so it's invisible to the plot, which only marks badge transitions (game-side). The
clean look is also the OCR confidence-rejection (badge diff>50 → None) doing its job. User
confirmed not-captured is intended.

## Session 2: Debug-panel shrink + de-jargon + full i18n

Took the OCR debug panel from a dev-internal readout to a public-facing one in three moves,
all driven by the user as the visual judge (live `preview_debug_panel.py` loop, screenshots
not Read back).

- **Layout**: 3-row → 2-row, panel 80→54px. Regrouped by *meaning*, which the user named as the
  organizing principle: line 1 = the driver's *interpretation + action* (state + segment + played
  + auto-played chip), line 2 = the *raw OCR reads* (state/speed/limit/distance/stop-offset). The
  730px width is cheap; vertical height was the thing to minimize.
- **De-jargon**: the load-bearing reframe — *"this debug panel was our internal jargons, I need to
  carry this out in a somewhat publically understandable format."* `Game Sync`→`Auto-PA` (the
  subsystem announces, doesn't drive — "Auto-Driver" rejected for implying it drives the train),
  `badge:`→`state:`, `Auto-fired`→`Auto-played`, internal fire-names (`departure`/`at-station`)→
  public (`Next stop`/`At station`). `OCR` kept verbatim (user already seeded the term with users).
- **i18n**: full `panel.*` key set across en/zh_HK/zh_CN, drafted rule-by-rule (zh_HK first, then
  zh_CN), user correcting each term as the zh authority (時速 not 速度, 儲存駕駛記錄 vs CN 保存速度曲线
  — en/zh wording deliberately allowed to diverge). `setup.ocr_state` term synced HK+CN.

Two non-obvious technical resolutions:
- **Two-font split** (→ conventions.md): the en chrome face (HelveticaNeue) is Latin-only, so
  kanji station names tofu under it. Chrome labels render via `i18n.font()`, station names via a
  dedicated CJK `_get_name_font()`. Then the user caught zh_CN segment misalignment → **baseline-
  align** (place each chunk by its own ascent against a shared baseline; top-aligning misaligns
  because Noto and ShinGo ascents differ). zh_HK looked fine only because its chrome font *is* ShinGo.
- **Width-bound line 1**: scenario with PASSING + auto-played chip overflowed 730. Measured every
  realistic combo (not a synthetic all-fields worst case — that overstated it). Fix: drop the line-1
  `(Passing)` suffix (redundant — line 2 already shows `state: Passing`) and let the chip *supersede*
  the `Played: N/M` count for its 3s lifetime (they share the tail, never both shown).

Review loop: 1 cycle, 0 blocking, 2 warnings fixed (stale `_BTN_HEIGHT` comment, OCR-literal
exception comment). Resolved the standing `_LAYER3_HUMAN`-near-identity deferred finding — the
i18n surface it was waiting on now exists (`_STATE_KEY`).
