## Session: Yamanote STA refinement complete + sta-make skill workflow upgrades

The last big un-refined STA route. 30 stops, all now meet the by-ear gate AND the route-level convention. Two skill upgrades emerged from user-named workflow gaps; both landed during the session, not deferred.

### The work

Pre-existing yamanote state: 29 sta files (JY24_OSK appears twice as loop terminus), pre-formalization splits with integer sta_cut values, never through `verify_sta_listen.py`. Recent skill flow targets ~0.5 s pre-voice silence per `sta_cut = round(max(music_end, voice_start − 0.5), 1)`.

The verifier yielded 24 PASS / 6 FAIL initially. The PASSED files retained their original sta_cut values; FAILed files all had a similar pathology — sta_cut placed mid-music with a discrete loud KAK transient sitting between music end and voice start, then voice content (often attacking at digital ceiling). Yamanote recordings are normalized hot (−6 to −10 dB music, voice peaks at 0 dB), so the saikyo-era detector tools bracketed the music itself instead of the KAK.

### Hostile-recording combined-pass pattern (new in sta-make/SKILL.md)

User flagged the workflow inefficiency mid-session: each per-file fix was being iterated in 2-3 ffmpeg passes (KAK splice → user verifies → sta_cut adjustment → user verifies → silence pad → user verifies). Each round needed manual re-verification. Their phrasing: *"why are you not doing that while fixing the KAK sound and sta_cut position? because skill didn't tell you? it saves my verification time."*

Fix: combine all three operations into a single ffmpeg filter graph. Cut music body before its sharp natural end (smooths music exit), insert artificial silence via `anullsrc` to meet ~0.3 s pre-voice convention (yamanote files have no natural silence gap wide enough), skip KAK + first voice burst with `atrim`, crossfade both junctions with `acrossfade`, set sta_cut at start of inserted silence. Section added under Step 12 with the template ffmpeg command.

The artificial-silence insertion specifically — `anullsrc=channel_layout=stereo:sample_rate=22050,atrim=duration=<silence_dur>` — is the new technique for hostile recordings where the natural file structure can't yield the convention's silence pad.

### Route-level gap alignment (new in sta-make/SKILL.md)

User caught me declaring yamanote done after fixing only the 6 FAILed files. Their question: *"did you also ensure all tracks shared the similar silence after sta_cut?"*

Audit revealed huge variance across the 29 files: 3 SHORT (<250 ms, JY03_AKB at 49 ms!), 12 in target band, 14 LONG (>400 ms, JY02_KND/JY25_SGW/JY27/JY28_HMC at 800-940 ms). The variance was audible — PageUp on station X felt snappier than station Y on the same line.

Fix: route.json edit only for LONG (set new_sta_cut = round(voice_attack − 0.30, 1)); insert artificial silence at sta_cut for SHORT (no splice junction needed if the file is otherwise clean). Section added under Step 12 with the audit script + both fix templates.

End state: all 29 files in 263–370 ms range, mean 307 ms, median 304 ms.

## Session: speed-limit OCR `100`→`110` misread fix + score-gated two-try splitter (PM)

User flagged in today's chuo recording: 23/129 speed_limit samples reading as `110` while IRL was `100`, all at score 0.65. Pattern bursty on a stable IRL value — frame-level OCR variance, not a steady classifier failure.

**Initial misdiagnosis.** Assumed argmin's `0+0` blob splits asymmetrically → produces grammar-valid wrong `110` → bypasses equal_width because the existing 2-try logic short-circuits on first grammar-valid result. Diagnosis ~half-correct: the failure category was right, but the specific argmin output on saved-PNG replay was `160` (grammar-fail → equal_width fallback → correct `100`), not `110`. User had screenshotted a misread frame; running the production reader on it returned `100` correctly. The discrepancy taught a new debugging fact (codified below).

**Saved-PNG vs live-BGRA divergence.** Same wall-clock-second screenshot replays differently than the live dxcam BGRA frame because of sub-pixel column-density shifts during PNG roundtrip. A live `100`→`110` misread can saved-PNG-replay to `100`→`160` (grammar-fail) — same root cause family, different argmin output. Means: capturing corpus via external screenshot tool is unreliable; need to dump the same numpy cell the OCR loop saw.

**Misread dump hook.** Wired into AutoDriver: when a grammar-valid speed_limit reads below 0.75, save `sl_cell` to `_ocr_calibration/_misread_dumps/sl_<ts_ms>_score<NN>_read<NNN>.png`. `ts_ms` matches `int(ts*1000)` from JSONL for cross-reference. User did one chuo drive, captured 31 dumps (19 misread `110`, 12 low-score `100`).

**Empirical band split was clean.** Across all 31 dumps: argmin ∈ {grammar-invalid `160` @ 0.66, valid `100` @ 0.66}; equal_width = `100` @ 0.91-0.92 universally. The 0.65-0.66 vs 0.92+ gap is large enough for a confident threshold. Picked 0.85 — comfortable margin both sides; calibrated against the band.

**Score-gated splitter.** Replaced first-valid-wins with: argmin trusted only when grammar-valid AND `score >= ARGMIN_TRUST_SCORE` (0.85); below that, equal_width runs as second opinion and its grammar-valid result wins. Preserves correct behavior on cleanly-segmenting cases (where argmin scores high) while repairing the limit_100 `0+0` mode.

**Mislabeled calibration file.** When verifying the new threshold against the corpus, `limit_110.png` "regressed" to read `100`. Diagnostic showed argmin and equal_width producing identical bboxes on this file as on user's "100_readas_110" screenshot — suspicion: the file actually contains a `100` cell. Confirmed visually: yes, `_ocr_calibration/limit_110.png` had been authored as a `100` source. This invalidated the original docstring's "equal_width breaks limit_110" warning (it was based on a mislabeled file). User caught + provided a real `110` capture; replaced the file; verified both strategies converge on `110` cleanly (no merged blob) at 0.857. Threshold edge case — sub-pixel variance could dip live `110` reads below 0.85, but equal_width then agrees, so safe.

**Side: KNOWN_LIMIT_VALUES dict cleanup.** Closed a deferred-findings entry: normalized three intermixed naming conventions (`speed_limit_75`, `limit 65` with space, `limit_30` short prefix) to consistent `limit_<N>`. Added `limit_100` to the dict — extractor warns + skips on it (no equal_width fallback in extractor; argmin alone can't split `0+0`), but registers the canonical fallback case for any future extractor enhancement.

**Review-fix cycle 1.** Reviewer caught: (a) `_crop_cell`'s docstring forbids "pygame state from background thread" but the new dump helper uses `pygame.image.save` from the AutoDriver thread — clarified to scope the rule to display state only (image-encode is display-independent); (b) my TODO closure note inaccurately said `speed_limit_75` was "left as-is" when it was actually renamed — corrected per Verify-before-claiming. Two findings deferred (`_try_read_speed_limit`'s `| None` return type is dead; `MISREAD_DUMP_DIR` placement under sources-named folder).
