## What got done

### 1. Drive recorder — JSONL streaming logger
*Commit `5039d24`.* AutoDriver now opens a per-session log file at thread start (`_recordings/drive_<line>_<diagram>_<TS>.jsonl`, gitignored) and writes one line per OCR cycle. Three record types, discriminated by `_type`:

- **`meta`** (line 0, written once): route + per-stop dicts. Each stop carries `name`, `english`, `furigana`, `stops_here`, `scheduled_time`, `sta_code` — fully self-contained, plot tools never need to re-load `route.json`.
- **`event`** (on each badge transition): `arrival` / `departure` / `passing_start` / `passing_end` + `curr_stop`. Plot tools place stop markers directly off these — no need to derive from sample stream.
- **`sample`** (one per OCR cycle, ~5 s): full OCR fields with confidence scores + sim state (`curr_stop`, `cnt_pa`, fired flags, `segment_start_stop`).

Per-line `flush()` for crash safety — kill the app mid-drive, JSONL is intact and parseable up to the last sample.

**Schema discriminator quirk worth knowing**: `_stops_here` is `bool(s.get("time") is not None)`, NOT `bool(pa)`. Per project convention, passing-through stations have NO `time` field; stopping stations always have one (even `time: 0` for the start station). Earlier `bool(pa)` was wrong for terminus / start stations with empty `pa` lists.

### 2. State-machine PASSING fix
*Commit `8ac2b67`.* User drove Keiyo, observed: train arrived at 稲毛海岸 with no PA played at all. Live JSONL showed why:

The Keiyo 千葉みなと→稲毛海岸 leg crosses **千葉貨物** (Chiba Freight Terminal) — a non-passenger waypoint. The game's HUD flips badge to PASSING when crossing it. (Side note for future-Claude: don't assume "PASSING badge ⟺ non-passenger waypoint" — the badge fires for **both** non-passenger waypoints AND passenger passing-through stations like 幕張豊砂. The badge just means "the train is currently passing through *something*"; what kind of thing is independent of the badge.)

So: the segment started with `STOPPED→PASSING` (not `STOPPED→MOVING`), because the cargo terminal was so close to 千葉みなと that the badge flipped to PASSING immediately on departure. The detector previously only reset `departure_fired` / `arrival_fired` on `STOPPED→MOVING`. `STOPPED→PASSING` fell through silently — flags inherited `True` from the previous segment, the speed-crossing departure check short-circuited, the arrival check stayed gated on `badge==MOVING` (which never resolved within this segment for ~80s), and after the eventual `passing_end` the level test saw `arrival_fired=True` and skipped. Train arrived with no PA played.

**Fix**: `STOPPED→(MOVING|PASSING)` both reset flags. Symmetrically, `(MOVING|PASSING)→STOPPED` both emit the arrival event. Mid-segment `MOVING↔PASSING` transitions stay silent (they're legitimate within-segment waypoint crossings inside an already-active segment). Mirrored in `data_tools/capture_game.py` (1b standalone) for parity.

### 3. Interactive HTML drive report
*Commit `35c3d0a`.* New `data_tools/plot_drive.py`. Reads a drive JSONL and renders a self-contained HTML page (Plotly inlined, ~5 MB).

Layout:
- **Page header** — small "DRIVE REPLAY" eyebrow, route + diagram title, `<origin> → <dest> · date` subtitle. Top accent strip in the line's brand colour (Keiyo `#E60012`, Yamanote green, Saikyo green, etc. — small hardcoded lookup with sane fallback).
- **Metric card** — six cells (Duration, Stops, Top speed, Avg speed, Avg dwell, Dwell ratio) with subtle 1px gray dividers, tabular numerals.
- **Section cards** — default 5 stops per row. Each card has a numbered badge ("01", "02"…), section title (`<entry> → <last>`), and inline stats (Stops · Time · Top · Avg · Dwell). Sections share the same x-axis duration (the longest section's span + 5%) so minutes-per-pixel is identical across rows; shorter sections show empty space on the right edge — duration comparison is visual.
- **Each row anchors at its left edge with a station post**: the previous row's last arrival sits at this row's window start; drawing a post for it gives every row a station marker at its opening.
- **Station signposts** are solid vertical lines + white-on-coloured-bg badges. **Origin (drive's first arrival) is green; terminus (last arrival) is red; middle stops are accent blue.** Plus an amber dashed marker for passing zones.
- **Y-axis non-negative-clamped** (`rangemode="nonnegative"`) so pan/zoom can't dip below 0 km/h.
- **Hover tooltips** show full OCR fields per sample.

Schedule adherence was prototyped (compute total elapsed vs sum of `scheduled_time`) but **dropped** — user noted route.json's `time` field may not be accurate, so the comparison would be meaningless.

### 4. Debug-bar Report button
Pill-styled "Report ↓" button rendered in the top-right of the OCR debug panel. Click forwards through `app.py`'s `MOUSEBUTTONDOWN` handler (new) to `auto_input.handle_panel_click`, which spawns a daemon thread that calls `data_tools.plot_drive.render_html_report` against the live JSONL.

Background thread → simulator UI stays responsive. Re-runnable mid-drive — each click produces a fresh snapshot of whatever's been captured so far. If the user clicks before any log is open, the handler logs a one-line hint.

`PASimulator` gets a new `drive_log_path: Optional[Path]` attribute that AutoDriver populates when it opens a log. The lazy `from data_tools.plot_drive import …` inside the daemon thread defers the plotly + numpy pull until the user actually clicks (matters for the cold-start cost when auto-input is on but no plot is needed).

## Iterations on the plot dashboard (5 design rounds with user)

The HTML report went through several visual revisions based on user feedback. Worth capturing the path:

- **v1** (matplotlib PNG, 5 rows fixed) — abandoned before testing. User wanted interactive HTML.
- **v2** (single Plotly figure with subplots) — multi-row but `<table>` in the title broke Plotly's restricted-HTML title rendering. User: "Your table was broken in the rendering."
- **v3** — switched from a single Plotly figure to **a custom HTML page wrapping N independent Plotly figures, one per section**. Header / metrics / section cards are real HTML/CSS; charts are just the speed plot inside each card. This is the right architecture — Plotly is the chart engine, not the dashboard engine.
- **v4** — refined typography, added per-section stats strip in the section header, proper start/end station colours (green/red).
- **v5** — line-colour accent strip + schedule adherence pill (later removed).
- **v6** (current) — alignment of x-axis time-scale across all sections (longest span + 5%), each row anchors with a station post at the left edge from the previous row's last arrival, dropped schedule adherence per user's "time field may not be accurate" call.

**Lesson**: For a "dashboard with charts" pattern, Plotly's title HTML support is too restricted (no tables, complex layouts). Wrap multiple per-section charts in a real HTML page with CSS for everything around the charts. Saves you trying to bend Plotly into being a layout engine it isn't.
