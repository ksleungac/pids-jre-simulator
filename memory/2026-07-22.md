## Session: per-line shared audio pool — chuo migrated (#87), 1034T unblocked (#88)

Ran alongside a concurrent OCR session on the same working tree; this block is data-only.

**The reframe that set the scope.** Opened as "add 1034T, the data has a lot of duplication". I costed the levers and initially ranked them by one-time saving — which was the wrong axis. The user corrected it: *"the infrastructure saves size, or 'does not bump size up' when new diagram, not necessarily to compress current chuo size."* Slope, not intercept. That single sentence decided the PA rule: existing takes are kept, not merged, because the win comes from a *new* diagram referencing slugs the pool already has. Everything I'd argued about collapsing 12.6 MB was beside the point.

**Where I burned the most rounds, and why.** Deciding what could be shared meant answering "are these two files the same recording", and I got it wrong three times in a row — byte hash, then a 5 ms-grid cross-correlation, then whole-file chroma. Each report was *faithful to its tool*; none of the tools could answer the question. The user caught all three from domain knowledge (*"don't just take filename"*, *"all sta in chuo are just the same"*, *"they are the same, else you can create a script for me that plays 2 side by side"*), and was right every time. The pattern only broke when I stopped picking a method and started calibrating one against a known-answer case. → `principles.md § "A measurement is a claim until the instrument is calibrated"`.

The corollary that cost the most: I'd concluded "PA is 0% shareable" from the broken correlation and built a whole design around it. The user's rebuttal was domain knowledge, not measurement — JR East states the stopping pattern when leaving a big station, so small-station approach announcements are shared while type-declaring departures are not. Transcribing (faster-whisper) rather than correlating confirmed it, and the boundary turned out to be geographic: east of 中野 both diagrams share a stopping pattern, so every announcement matches.

**Two designs killed, both correctly.** A `line.json` holding a shared station spine — user: *"keep current data format, just dat ais shared… surgery changes please."* And a diagram-folder-then-pool path fallback, which a `/third-man` killed by citing this repo's own `critical_lessons §2`: legacy PA slugs are diagram-local, so a missing file would silently resolve to the pool and play *a different announcement*. I had picked the fallback precisely because it needed no data change — optimising for a small diff and buying a silent-failure mode. (`principles.md` gained "A fallback must be STRICTER than the path it replaces" this same session, from the other track.) The third-man also said ship STA-only; that one didn't survive contact, because `audio_root` moves `pa/` and `sta/` together.

**Why the migration was done by hand.** I wrote one script to both derive and apply the renames. Its dry run got two decisions wrong — too-strict identity, and a train-type suffix on the 東京 announcement because that announcement names 総武快速線. User, before seeing the second bug: *"script is where you will things wrong."* Doing it by hand against a checked table surfaced two more script errors. → `principles.md § "Hand-author the mapping; a script only executes it"`.

**Verification that actually discriminates.** `validate_data` passing meant nothing until a mutation proved it could fail — a bogus slug does surface (`pa/kanda-arr-DOES-NOT-EXIST.mp3 missing`). Runtime paths checked separately, since the validator and `AudioPlayer` could have diverged.

Left uncommitted on `master` by request. A branch was considered and deferred — the concurrent session has an unpushed commit and a staged deletion in the shared tree, so branching would isolate nothing.

## Session (block 5): OCR capture hardening — three fixes, three of my own errors caught by measurement

Continuation of the #82 night. User drove three collection runs (2442 frames) plus supplied their reporter's H.264 screen recording; every conclusion below came from that data, and three confident hypotheses of mine died against it.

**The through-line: I kept inferring where I could have measured.** (1) Diagnosed the `4` template as weak from one run's scores — the tunnel run showed the same template at 0.957, best of any digit. (2) Blamed DPI 125% — the user's 125% run had *identical* HUD geometry and *less* clipping than the 100% run. (3) Claimed a fixture's true value was 47.7 by reading a NEIGHBOURING frame's filename, invented a "bled 7 reads as 8" defect from it, filed #86, and wrote it into the README and a test docstring. Rendering the glyphs as ASCII took one command: two closed counters, it is an `8`, the cell is 48.3, and the read was already correct. #86 closed as not-a-bug, all four sites corrected. → `principles.md § "Verify before claiming"`.

**What was actually wrong.** A digit SHEDS a 1-column stub on a degraded frame, dimensionally identical to a decimal point, and the decimal scan took it → `48.3` read as `4`. This is a regression from the 2026-07-20 one-column tolerance: widening the dot scan to catch a faint dot is exactly what admits stubs. The two are a matched pair — `DECIMAL_MIN_GAP` is the counterweight, and neither may be removed without the other.

**The root cause underneath everything.** `DARK_THRESHOLD = 70` is a fixed global constant deciding "ink vs background" while the HUD is *semi-transparent* — background scenery brightness moves the levels under the text. Bright surface → edge column clipped (glyph narrows, template mismatch); dark tunnel → glyph bleeds fat. Same constant, opposite failures. The tunnel run being the CLEANEST of the three is what proved it: I had predicted tunnels would degrade worst.

**The measurement mistake worth remembering.** I judged the tolerant-matching change by top-2 margin, saw it collapse 51→381 glyphs under 0.10, and nearly reverted. Accuracy under degradation went 92.8%→100%. Tolerance lifts the runner-up with the winner: margin compresses, ordering survives. → `principles.md § "Validate against the outcome, not a proxy"` (new).

**On the user's "IRL OCR handles far worse" point** — correct, and the gap is structural, not hard: we binarize on a fixed global constant, match on binary pixel equality rather than grayscale NCC, and use a threshold-derived tight bbox as the registration reference (the wobbliest measurement is the anchor). Latency was never the constraint — ~10ms/frame against a 330ms budget.

**Subagent evaluations** (2442 frames): adaptive Otsu clamped `[55,100]` with a contrast fallback — purity 89.2%→95.1%, clipped forms to zero, empty cells still safe (bare Otsu hallucinates `"77600"` from sensor noise). Grayscale NCC vs binary — **identical reads on 6872 live glyphs**, so no measured matching defect; NCC only wins on downscale-then-erode, which is what the `WIP_ocr_multiresolution.md` 1080p-canonical path will produce → deferred there, not adopted now.
